# Phoenix OS 0.37.0

**Released:** 2026-08-30

Phoenix OS 0.37.0 accepts RFC-0037, Durable Runs, Recovery, and Reliability
Hardening.

## Highlights

- Deterministic Phoenix-owned crash/failure injection at reviewed durable boundaries, with no production configuration path for enabling the test injector.
- Explicit `CONFIRMED_COMMITTED`, `CONFIRMED_NOT_COMMITTED`, and `COMMIT_OUTCOME_UNKNOWN` handling that resolves ambiguous durable writes through exact authoritative re-read rather than blind replay.
- Strong adversarial checkpoint integrity coverage for corruption, truncation, substitution, rollback, sequence, digest, and stale-head failures.
- Exhaustive lease-fencing/takeover and concurrent-recoverer evidence proving stale workers cannot mutate current durable state.
- Crash-safe `PREPARED` / `STARTED` / `INDETERMINATE` handling with no transparent replay of possibly started model or tool effects.
- Fresh current resume authority plus current profile, tool, schema, model/provider, resolver, approval, and protection availability after restart.
- Original deadline, monotonic finite budgets, cancellation continuity, bounded persistent recovery attempts, retention fencing, and stale-backup anti-resurrection.
- Content-free reliability administration plus a dedicated deterministic network-free `check_reliability_release.py` release gate.

## Security

Recovery is continuation under fresh evidence, never replay by assumption. A restart
cannot increase authority, budget, lifetime, or certainty.

Persisted checkpoints remain untrusted data and never grant current authority. A
recovered protected operation must satisfy the same fresh canonical authorization
required without a restart. Historical authorization, expired/consumed/revoked
approvals, stale configuration, or stale dependency identity cannot be revived by
durable metadata.

An unknown durable commit outcome is not interpreted from a local success or
exception. Phoenix re-reads the authoritative durable state and requires the exact
intended run version, checkpoint sequence, digest, transition, and attempt/
reconciliation identity before treating the mutation as committed.

Fencing generation remains authoritative for durable ownership. Stale workers cannot
append, complete, cancel, reconcile, clean up, terminalize, or overwrite state after a
newer generation takes ownership.

A model or tool attempt whose external completion is uncertain remains
`INDETERMINATE`. Missing terminal evidence is not proof that the effect failed, and
idempotency keys are risk reduction rather than exactly-once evidence.

The original finite deadline survives restart and downtime counts against it. Consumed
step/call/token/byte budgets do not reset, current stricter limits may reduce remaining
capacity, and cancellation prevents new protected work after recovery.

Store freshness evidence and tombstones prevent reviewed stale-restore resurrection.
When freshness cannot be established, automatic recovery pauses rather than guessing.
Routine reliability output remains content-free.

## Compatibility and migration

Phoenix OS 0.36.0 behavior remains compatible when durable execution is omitted.
RFC-0028 remains the sole durable-run state machine and RFC-0036 continues to compose
that primitive for integrated durable recovery. RFC-0037 adds reliability evidence and
fail-closed hardening rather than a second durable engine or authority model.

The durable SQLite reference schema is version 5 for the v0.37.0 release. Migration
adds persistent bounded recovery-attempt bookkeeping and store-freshness evidence while
preserving existing checkpoint/state-machine semantics. Configured stores may use a
separate freshness witness to detect reviewed stale-backup restoration classes.

Do not perform an in-place downgrade of schema version 5, edit durable schema metadata,
delete recovery-attempt counters, or rewrite freshness evidence to force an older
runtime to accept newer durable state.

See
`docs/migrations/v0.36.0-to-v0.37.0-durable-recovery-reliability.md` for schema,
freshness-witness, recovery, retention/backup, release-gate, and rollback guidance.

## Release validation

The release must pass:

```bash
ruff check .
ruff format --check .
mypy
pytest
python scripts/check_integrated_agent_release.py
python scripts/check_reliability_release.py
```

The dedicated reliability gate runs the reviewed durable/integrated reliability
surface, verifies the exact 48-invariant threat review and reliability matrix,
rechecks the production fault-injection boundary, validates wheel and sdist contents,
rebuilds a wheel from the validated sdist, and installs both wheel forms with
`--no-deps --no-index` in isolated environments.

All prior named release gates and the full `scripts/check.ps1` repository gate remain
release blocking. The normal GitHub Actions Python 3.12/3.13 matrix must be green for
the exact S8 release commit and again for the post-merge `main` commit before release
publication.
