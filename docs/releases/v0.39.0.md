# Phoenix OS 0.39.0

**Release candidate prepared:** 2026-09-13
**Publication:** pending

Phoenix OS 0.39.0 release-candidate metadata covers RFC-0039 usable real-task operation
and controlled workspace mutation. RFC-0039 remains Proposed at this stage. Candidate
metadata does not authorize acceptance, tagging, merge, push, or publication.

## Highlights

- Official `phoenix config`, `phoenix doctor`, and `phoenix task` paths provide the
  operator-facing normal path for real-task execution.
- Development checkouts use explicit trusted roots and bounded `read_prefixes` /
  `patch_prefixes`.
- `workspace.list` and `workspace.read` remain bounded, authorized, and current-run
  freshness evidence rather than ambient filesystem authority.
- `workspace.patch` is constrained to observed UTF-8 files beneath configured patch
  prefixes and rejects protected, stale, binary, special, reparse, metadata-unsafe,
  oversized, and unobserved targets.
- Trusted review renders a bounded exact diff; approval binds to the exact prepared patch.
- Final commit revalidation prevents stale authorization and stale replacement.
- Patch results remain content-free and expose bounded operator review metadata.

## Security

Model output and workspace content remain data, not authority. A model cannot grant itself
filesystem, Git, shell, provider, policy, approval, or patch authority.

Patch preparation and commit remain fail-closed across path traversal, aliasing, VCS
metadata, active configuration/policy/state, active runtime/venv targets, stale digests,
resource rebirth, reparse/special files, metadata hazards, bounds, deadline/cancellation,
and indeterminate-effect recovery.

Git mutation, arbitrary shell, generic filesystem write, cloud routing, desktop-wide
control, and connector expansion remain outside RFC-0039 v0.39 scope.

## Compatibility and migration

Existing v0.38 provider-neutral behavior remains the default when new configuration is
omitted. Existing RFC-0031 workspaces remain unchanged unless an explicitly registered
development checkout adapter is configured. Package installation alone enables no model,
provider, workspace, tool, or patch authority.

See
`docs/migrations/v0.38.0-to-v0.39.0-usable-real-task-operation-and-controlled-workspace-mutation.md`
for operator, migration, rollback, and release-candidate guidance.

## Dogfood and operations

Real-provider dogfood remains separately invoked and must not become an ordinary CI
dependency. The v0.39 dogfood must use an official candidate wheel installed into a clean
virtual environment and must use the official product path without a custom Python
composition helper.

The normative checklist is
`docs/rfcs/RFC-0039-real-provider-dogfood-checklist.md`. Its required items remain open
until the operator runs and reviews the real-provider procedure.

The release candidate should exercise 10-20 normal tasks across more than one task shape
before publication.

## Release validation

The final v0.39 release gate remains pending and must include:

- full repository quality gate;
- selected RFC-0038 regression suites;
- RFC-0039 deterministic CLI/config/doctor/task tests;
- RFC-0039 workspace patch security/adversarial matrix;
- RFC-0037 recovery regression for patch indeterminate effects;
- package build and structural inspection;
- wheel rebuild from validated sdist;
- isolated offline install of original and rebuilt wheels;
- packaged `phoenix --help`, `phoenix config --help`, `phoenix doctor --help`, and
  `phoenix task --help` smoke tests without source imports;
- separately invoked real-provider dogfood;
- proof that normal-path dogfood used no custom Python composition helper.

Ordinary CI remains deterministic and network-free.
