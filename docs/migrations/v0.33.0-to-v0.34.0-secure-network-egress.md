# Migrating Phoenix OS 0.33.0 to 0.34.0

Phoenix OS 0.34.0 adds RFC-0034 secure network egress and controlled HTTP
operations as an explicit opt-in capability. The upgrade does not convert any
existing network behavior into ambient HTTP authority.

## Compatibility

When network-egress configuration is omitted, Phoenix OS preserves v0.33.0
behavior. Upgrade creates no egress profile, operation, policy grant, credential
binding, network request, DNS lookup, socket, Runtime service, worker, or remote
effect automatically.

Existing RFC-0024 webhook delivery and RFC-0026 model-provider networking retain
their existing canonical authorizers, endpoint policies, transports, retry
semantics, and lifecycle ownership. Phoenix OS 0.34.0 does not silently route
either subsystem through `NetworkEgressService`.

No existing permission is interpreted as `network.http.request`.

## Authority model

Every controlled request targets
`network-egress:<profile-id>/generation:<generation>/operation:<operation-id>`.
The profile ID, positive generation, and operation ID are trusted Phoenix-owned
state. A caller or model does not supply a raw URL, scheme, hostname, port, DNS
resolver, proxy, TLS policy, redirect policy, credential, literal destination
address, HTTP method, request target, or arbitrary header.

For model-originated requests, `tool.invoke` and `network.http.request` remain
independent requirements. An allow at one boundary does not satisfy the other.
Effective authority is the intersection of current subject, policy, exact
profile/operation intent, profile generation, credential lease when configured,
destination admission, cancellation/deadline state, and the canonical network
boundary.

## Disabled-first rollout

1. Upgrade to Phoenix OS 0.34.0 without adding network profiles or policy grants.
2. Run the complete regression suite and `python scripts/check_network_egress_release.py`.
3. Define only reviewed server-owned profiles and operations for required destinations.
4. Keep remote destinations on verified HTTPS; use plain HTTP only for explicitly configured loopback targets.
5. Grant `network.http.request` only for exact generation-bound resources.
6. For model-originated network tools, preserve independent exact `tool.invoke` authority.
7. Add exact-version `SecretRef` bindings only where required; never place plaintext credentials in caller/model data or logs.
8. Enable Runtime ownership only after profile, policy, destination, credential, and finite-limit review.
9. Treat `network.egress.health.read` as inspection authority only.

## Destination and transport checks

Hosted remote profiles require verified HTTPS. DNS resolution is bounded and the
complete answer set must pass the active server-owned address policy. Unsafe
answers fail the request rather than being discarded while other answers proceed.
Connection attempts use only admitted literal addresses while preserving the
canonical hostname for hosted TLS SNI and certificate validation. Ambient proxy
configuration is ignored. Redirects are not followed.

HTTP CONNECT, TRACE, protocol upgrade, generic WebSocket, raw sockets,
caller-selected DNS/proxying, and browser navigation remain outside v0.34.0.

## Freshness and external effects

A successful early authorization is point-in-time data, not a bearer capability.
After the final attacker-controlled network wait and before the protected send,
Phoenix revalidates the exact credential lease when configured, current RFC-0033
subject freshness, exact `network.http.request` authority, cancellation/deadline,
current complete profile/operation state, and pinned destination admission.
Do not insert an attacker-, observer-, audit-, event-, health-, or
inspection-controlled blocking wait into that final admission-to-send window.

Once HTTP request bytes may have started, an ambiguous failure is indeterminate.
Do not transparently reconnect, select another address, retry, or claim rollback.

## Response handling

HTTP status, exposed response headers, and response bodies are bounded untrusted
data. Response URLs, redirect locations, tokens, policy-like text, model
instructions, or tool results never create another request or other authority.
Automatic redirects, cookie jars, browser sessions, automatic workspace
downloads, and response-driven protected operations remain outside RFC-0034.

## Rollback

1. Stop admitting new network-egress work and remove or disable relevant grants.
2. Remove or disable configured network-egress Runtime composition.
3. Preserve existing webhook and inference configuration unchanged.
4. Do not turn stale-profile, stale-subject, credential, cancellation, destination, or policy denial into allow for compatibility.
5. Do not automatically retry an operation whose request bytes may already have reached the remote peer.
6. Restore Phoenix OS 0.33.0 only after admitted work has been handled according to existing indeterminate-effect semantics.

Network response data and health/observability output are non-authoritative and
require no migration into v0.33.0 authority state.
