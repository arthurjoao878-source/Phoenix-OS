# Migration: Phoenix OS v0.37.0 to v0.38.0 real-provider execution and dogfood

RFC-0038 adds secure real-model provider execution through the existing RFC-0026
inference boundary and connects that path to the existing RFC-0027 agent model-turn
semantics. It does not create a parallel provider authority model, a second agent loop,
an automatic provider installer, an automatic model manager, or a transparent
external-effect retry mechanism.

This document is migration, dogfood, operator, and rollback guidance for the
v0.37.0 -> v0.38.0 transition. Earlier Slice 7 gates intentionally kept the package
version at `0.37.0`; the version changed only in the dedicated release-finalization
step after the preceding evidence was green.

## Compatibility default

No migration action is required when real-provider execution and real-agent dogfood are
omitted.

Existing deterministic inference remains valid. Existing deterministic agent tests and
Runtime composition remain valid. v0.37 durable/recovery behavior remains unchanged.
Phoenix does not contact a provider, install a model, create a credential, register a new
tool, or grant additional authority merely because RFC-0038 code is present.

The provider-neutral package retains no mandatory runtime dependency. Provider-specific
integration remains explicit.

## Provider activation and configuration

Real-provider execution is opt-in and requires explicit trusted configuration.

For the local reference provider, the reviewed deployment binds an explicit RFC-0026
loopback endpoint and port, an exact Phoenix model identity, and the provider-native model
name. Deployments may additionally bind a reviewed provider model revision/digest when
the provider exposes suitable evidence.

Use finite trusted context/output limits. A provider-advertised larger context window
does not enlarge Phoenix limits. Caller-supplied `InferenceRequest.parameters` are not
copied wholesale into provider-native options; only explicitly reviewed Phoenix-owned
parameters with bounded type/range/enum semantics may translate.

Phoenix does not:

- automatically install Ollama or another provider;
- automatically download/pull/delete models or mutate provider model inventory;
- automatically kill/restart provider processes;
- derive provider authority from ambient proxy/redirect settings;
- grant endpoint or credential authority through model/provider discovery;
- automatically fail over from local to hosted/cloud providers.

There is no automatic local-to-cloud fallback.

Provider process lifecycle, model installation, and model inventory remain operator
responsibilities.

## Agent model-turn and tool behavior

RFC-0027 remains the agent authority/execution path. Real model turns pass through
RFC-0026 and then return only the Phoenix-owned structured model-turn envelope.

For v0.38.0, the reviewed structured path supports exactly one final result or one tool
proposal per turn. Multiple proposals, mixed final/tool outcomes, unknown tools, and
malformed tool data fail closed before normal authorization/execution.

Native Ollama tool calling remains disabled until semantic equivalence to the existing
RFC-0027 admission, validation, approval, authorization, and execution path is proven.
Provider-native model output does not gain direct tool authority.

## Dogfood profiles

The initial real-task profiles deliberately reuse/narrow existing Phoenix capabilities.

Development dogfood is limited to the reviewed advisory/read-oriented surface needed by
the implementation. It does not add unrestricted shell, PowerShell, arbitrary filesystem
access, autonomous test-process authority, repository writers, or Git lifecycle tools.

Research dogfood reuses bounded memory/workspace reads plus the reviewed network/browser
boundaries and configured navigation targets. It does not turn browsing or network
results into new provider, credential, or filesystem authority.

Desktop/integrated dogfood reuses reviewed host process/window observation boundaries. It
does not grant arbitrary host control merely because a real model is present.

Commit, push, merge, tag, release publication, provider installation, and model inventory
mutation remain outside the initial autonomous tool set.

## Durable recovery and uncertain provider attempts

Restart remains continuation under fresh evidence, never replay by assumption.

Real-provider durable recovery revalidates current provider/model identity, profile,
tools, schemas, policy, configuration, and other compatibility evidence. Original finite
deadlines survive restart, consumed budgets remain monotonic, and cancellation continuity
blocks new protected work after cancellation.

A provider/model attempt that may have started but lacks trustworthy terminal evidence
must not be transparently replayed. Missing evidence is not proof that the external
attempt did not happen. Indeterminate attempts remain in the existing durable
reconciliation path.

Do not convert provider disappearance, restart, timeout, cancellation, or uncertain
external completion into automatic provider fallback or retry.

## Provider failure and operator diagnostics

Expected fail-closed operational cases include:

- provider unavailable or transport unreachable;
- provider timeout;
- configured model missing;
- reviewed model revision/digest mismatch;
- malformed/truncated/oversized provider response;
- missing terminal streaming evidence;
- cancellation during provider execution;
- provider/model/profile/tool/schema/policy drift at durable resume.

Provider health/operator diagnostics are content-free. Routine durable evidence must not
persist prompts, model responses, tool arguments/results, workspace contents, memory
contents, browser contents, clipboard contents, credentials, or secrets.

## Dogfood guidance

Real-provider canaries are explicit operational procedures outside mandatory CI.

A reviewed local dogfood run should:

1. start from explicit trusted provider/model/profile configuration;
2. verify the intended provider/model is available without Phoenix mutating provider
   process or model inventory;
3. run representative development, research, and desktop/integrated tasks through the
   normal RFC-0026/RFC-0027 boundaries;
4. exercise provider/model disappearance, timeout/cancellation, restart/revalidation,
   deadline/budget continuity, and revision drift where provider evidence is available;
5. confirm there is no automatic local-to-cloud fallback and no transparent replay of an
   indeterminate provider attempt;
6. record only bounded content-free operational evidence;
7. leave paid/network canaries outside mandatory CI.

A real-provider canary failure blocks release when it demonstrates a Phoenix contract
violation. A failure caused solely by a documented external provider outage may be
classified separately, but it must not be converted into a passing Phoenix result.

## Rollback guidance

Disabling or omitting real-provider/dogfood configuration returns Phoenix to its
provider-neutral compatibility path; it does not require Phoenix to uninstall providers,
delete models, or mutate provider inventory.

Do not use rollback as justification to replay an indeterminate model/tool attempt,
increase remaining deadlines/budgets, revive stale approvals, or bypass current
provider/model/profile/tool/schema/policy revalidation.

Phoenix does not automatically kill/restart Ollama or rewrite its model inventory during
rollback. Provider/model lifecycle cleanup remains an explicit operator action outside
Phoenix authority.

If a deployment added provider-specific trusted configuration, retain or remove that
configuration deliberately under normal configuration/change control. Do not reinterpret
ambient environment variables, proxy settings, provider discovery, or cached provider
metadata as equivalent authorization.

## Release-gate adoption

The v0.38.0 release-finalization sequence requires:

- the complete existing project quality gate;
- RFC-0038 deterministic provider/model-turn gates;
- RFC-0037 adversarial reliability gate;
- the complete real development/research/desktop dogfood checklist;
- review of all dogfood-discovered security/reliability issues;
- wheel and sdist build validation;
- isolated offline installation;
- proof that package import and normal tests require no provider/model/API;
- these release notes and migration/dogfood guidance;
- the package version change from `0.37.0` to `0.38.0` only after the preceding evidence;
- RFC-0038 acceptance only after all required evidence is green;
- tag/publication only after the normal release authorization/gates.

Mandatory CI remains deterministic and network-free. Real Ollama/hosted-provider canaries
are separate explicit dogfood procedures.
