# Migration: Phoenix OS v0.36.0 to v0.37.0 durable recovery reliability hardening

RFC-0037 hardens the existing RFC-0028 durable-run and RFC-0036 integrated durable
recovery path. It does not add a second durable state machine, checkpoint format,
authority model, workflow engine, or transparent external-effect retry mechanism.

This document is migration and rollback guidance for the v0.36.0 -> v0.37.0 transition.
The S7 implementation slice intentionally keeps the package version at `0.36.0`; the
version changes only in the RFC-0037 release-finalization slice.

## Compatibility default

No migration action is required when durable execution is omitted.

Existing non-durable RFC-0027 agent execution remains unchanged. Omission of integrated
execution also preserves the existing non-integrated behavior. Enabling durable recovery
does not grant new authority: current policy, current configuration, current dependency
identity, current approvals, current limits, current deadline, and current cancellation
remain authoritative after restart.

RFC-0028 remains the only durable-run state machine and RFC-0036 continues to reuse it.

## Durable SQLite migration

The RFC-0037 implementation advances the durable SQLite schema used by the release
candidate to schema version 5.

The migration retains existing durable checkpoint bytes and state-machine semantics while
adding bounded recovery-attempt bookkeeping and store-freshness metadata required for
finite automatic recovery and stale-restore detection. Migration tests cover upgrade from
the released pre-RFC-0037 durable schemas to the current schema.

A configured SQLite store also uses a bounded freshness witness. The default witness is
the sibling `<database>.freshness` path. Deployments that require stale-backup detection
across restoration domains should configure the witness outside the database backup
domain and preserve its access controls separately.

The witness contains only store identity/generation evidence. It is not an authority
token, checkpoint, prompt, model response, tool argument/result, credential, approval,
or protected payload.

A missing, malformed, identity-mismatched, or newer-than-restored witness makes automatic
recovery fail closed. Phoenix does not guess that a restored active record is current.

## Recovery behavior

Restart is continuation under fresh evidence, never replay by assumption.

Operators should expect stricter fail-closed outcomes after upgrade when Phoenix cannot
prove current compatibility, ownership, write outcome, external-effect disposition,
deadline, budget, cancellation state, or store freshness.

Important behavior includes:

- unknown durable mutation outcome is resolved by authoritative re-read and exact
  version/sequence/digest/transition comparison;
- stale fencing generations cannot append, complete, cancel, reconcile, clean up, or
  terminalize current durable state;
- a `STARTED` model/tool attempt is never transparently replayed after restart;
- indeterminate external effects remain in the RFC-0028 reconciliation path;
- current `agent.resume` authority and current dependency/profile/schema/model/tool
  compatibility are revalidated after restart;
- consumed, expired, revoked, or mismatched approvals are not revived;
- the original total deadline is preserved and downtime counts against it;
- consumed finite budgets remain monotonic and current stricter limits may reduce
  remaining capacity but cannot silently enlarge it;
- cancellation continuity blocks new protected model/tool work;
- automatic recovery attempts are persisted and finite;
- restore ambiguity pauses automatic recovery rather than resurrecting stale state.

Routine reliability administration remains content-free.

## Retention and backup operations

Retention cleanup remains fenced and cannot delete an actively/currently leased run.
Prepared reconciliation keeps its real lease until apply/discard/expiry, so cleanup
cannot race through that ownership boundary.

Terminal tombstones and store freshness evidence protect against automatic resurrection
from stale active records. Backup procedures should treat the SQLite database and the
freshness-witness policy as one reviewed operational design even when they intentionally
reside in different backup domains.

Do not copy an older database over a newer live database and then delete or rewrite the
freshness witness to make the restore appear current. That discards the evidence RFC-0037
uses to fail closed.

## Rollback guidance

Rollback must preserve durable-state integrity; code rollback is not a schema downgrade.

Do not attempt an in-place schema downgrade from schema version 5 to an older durable
SQLite schema. Do not edit `PRAGMA user_version`, delete recovery-attempt counters, remove
store-generation metadata, or rewrite the freshness witness to make an older runtime
accept newer durable state.

If rollback to the released v0.36.0 runtime is required after a database has been opened
or migrated by v0.37.0 code, stop durable workers and restore a mutually consistent
v0.36.0-era database backup under the v0.36.0 operational procedure. Keep newer state
quarantined for investigation rather than merging histories by hand.

Runs with uncertain external effects must remain indeterminate across rollback planning;
operator convenience is not evidence that the effect did not happen.

## Release-gate adoption

S7 adds the dedicated network-free RFC-0037 reliability gate:

```text
python scripts/check_reliability_release.py
```

The gate executes the reviewed durable/integrated reliability regression surface,
validates the reliability matrix and threat review, proves ordinary packaged composition
does not expose the deterministic fault injector, builds wheel and sdist, rebuilds a
wheel from the sdist, and runs isolated offline artifact smoke checks.

The gate is wired after all prior named release gates in `scripts/check.ps1`,
`scripts/check.sh`, and CI. S7 does not change `pyproject.toml`, `CHANGELOG.md`, release
notes, tags, checksums, artifacts, or GitHub Release state. RFC-0037 S8 performs those
release-finalization actions only after S1-S7 gates are green.
