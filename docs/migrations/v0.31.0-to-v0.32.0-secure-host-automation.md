# Migrating from Phoenix OS v0.31.0 to v0.32.0 secure host automation

Phoenix OS v0.32.0 introduces the optional RFC-0032 secure host-automation and
desktop-control subsystem. The safe first upgrade keeps host automation absent from
Runtime composition.

Desktop state is data; host effects require fresh authority. Installing v0.32.0 or
configuring a host adapter does not grant `host.process.list`, `host.window.list`,
`host.app.launch`, `host.window.focus`, `host.app.close`, `host.clipboard.write`, or
`host.clipboard.read`; does not grant `tool.invoke`; and does not turn process metadata,
window metadata, configured-application labels, clipboard text, model output, tool
results, prior enumeration, prior approvals, or adapter state into Phoenix authority.

## Compatibility baseline

When no host-automation adapter is supplied to Runtime composition:

- no `host`, `host.health`, or `host.administration` service is created;
- no `WindowsHostAutomationAdapter`, process/window discovery backend, application
  profile, clipboard backend, or native operating-system handle is created merely by
  importing Phoenix;
- no process or window is enumerated;
- no application is launched, focused, or closed;
- no clipboard value is read or written;
- no principal receives any `host.*` action automatically;
- no agent receives a host tool automatically;
- existing Phoenix OS v0.31.0 inference, agent, durable-agent, multi-agent, memory,
  workspace, policy, approval, audit, Control Plane, and Runtime behavior remains
  unchanged.

This is a migration-free-by-omission upgrade. Keeping host automation absent is the
first upgrade checkpoint and the fastest disable-first rollback point.

## Pre-upgrade inventory

Record:

1. the exact v0.31.0 package and rollback artifact;
2. the current Phoenix policy and agent-tool configuration;
3. the Windows account, interactive session, and desktop in which Phoenix will run;
4. one stable server-owned `HostId` for the first canary host;
5. every intended server-owned `HostApplicationId` and its reviewed Windows executable
   and optional working directory;
6. every proposed exact `host.*` policy edge and resource;
7. every model-facing host tool that should be exposed and its separate `tool.invoke`
   policy;
8. whether graceful application close must require the explicit host approval gate in
   addition to normal agent-tool approval;
9. whether clipboard read is genuinely required; it is separately configurable and
   should remain disabled otherwise;
10. conservative process/window enumeration, text-size, and operation-deadline limits;
11. one non-sensitive canary application and non-sensitive clipboard payload;
12. a rollback owner and maximum canary window.

Do not use the first canary to control an administrator desktop, privileged process,
password manager, terminal, shell, production editor with unsaved work, or another
sensitive interactive session.

## Stage 1: install with host automation absent

Install the v0.32.0 package while preserving the v0.31.0 Runtime composition and do not
supply a host-automation adapter.

Confirm that importing Phoenix or starting unrelated agent/workspace services does not
probe the desktop, create native handles, enumerate processes/windows, access the
clipboard, register host tools, or create `host`, `host.health`, or
`host.administration`.

Confirm that no existing policy rule is reinterpreted as host authority. `agent.run`,
`model.infer`, `tool.invoke`, `workspace.*`, `memory.*`, and every other pre-v0.32
action remain independent from `host.*`.

## Stage 2: define one bounded Windows canary host

Windows is the only concrete v0.32.0 adapter. Configure one reviewed
`WindowsHostAutomationAdapter` only on Windows and give it one stable server-owned
`HostId`.

Start with conservative `HostAutomationLimits` below the global ceilings for:

- process results;
- window results;
- process-label characters;
- window-title characters;
- clipboard text characters;
- clipboard text bytes;
- operation timeout.

Keep `application_profiles=()` for the first read-only discovery canary when practical,
and keep `clipboard_read_enabled=False`.

Explicit Windows-adapter configuration on an unsupported platform must fail safely.
Omitting host automation must remain a no-op and must not probe the operating system.

## Stage 3: grant exact read-only host policy first

Start with only the read-only discovery actions required by the canary:

```text
host.process.list
host.window.list
```

Use the exact server-owned collection resources:

```text
host-automation:host:<host-id>/processes
host-automation:host:<host-id>/windows
```

Each host action is independent. Do not infer host permission from another `host.*`
action, `agent.run`, `model.infer`, `tool.invoke`, `workspace.*`, `memory.*`, previous
enumeration, model output, or approval-like text.

Verify that current host policy immediately wins over prior enumeration, historical
approval, persisted execution data, or adapter state. Revoke one discovery grant and
confirm the next exact operation fails closed.

## Stage 4: validate bounded process and window discovery

Exercise one small process-list request and one small window-list request.

Verify that:

- results are bounded by configured limits and operation deadlines;
- public process/window identities are Phoenix-owned opaque identities rather than raw
  PID/HWND authority;
- results carry the current finite `HostEpoch`;
- process results do not expose raw command lines, environment blocks, process memory,
  access tokens, handles, or unrestricted executable paths;
- window titles remain untrusted potentially sensitive data;
- titles, clipboard text, native identifiers, executable paths, and raw OS failures do
  not enter routine operational telemetry;
- enumeration itself grants no launch, focus, close, clipboard, keyboard, mouse,
  filesystem, shell, or administrator authority.

Restart or otherwise replace the adapter boundary and verify old process/window
identities fail closed rather than resolving to a reused native target.

## Stage 5: add one server-owned application profile

Only after read-only discovery is stable, add one reviewed `WindowsApplicationProfile`
with a server-owned `HostApplicationId`, trusted executable path, and optional trusted
working directory.

The launch profile is trusted deployment configuration. A public or model-originated
launch request names only the configured application identity. It does not accept a
model-selected executable path, command line, working directory, environment block,
shell verb, elevation request, package identifier, or native launcher.

Grant only:

```text
host.app.launch
```

for the exact configured resource:

```text
host-automation:host:<host-id>/application:<application-id>
```

Launch one non-sensitive canary application. Verify that its result is descriptive
data and grants no later process/window authority. Do not transparently retry an
uncertain or timed-out launch; if Phoenix loses certainty after effect admission, treat
the outcome as indeterminate.

## Stage 6: validate exact stale-safe window focus

Enumerate windows again and select one canary window using its Phoenix-owned
`HostEpoch`, `HostWindowId`, `HostProcessId`, and configured application relation when
present.

Grant `host.window.focus` only for the exact Phoenix window resource:

```text
host-automation:host:<host-id>/window:<window-id>
```

Verify that focus revalidates the native target immediately before the effect. A
vanished window, reused native handle, changed process relation, changed host epoch, or
unsafe session/desktop condition must fail closed rather than retargeting by title or
label.

Successful focus does not guarantee that focus persists and grants no keyboard or
mouse authority.

## Stage 7: validate graceful application close and approval

`host.app.close` is graceful close only in v0.32.0. It is not `process.kill`, and
failure to close gracefully must not widen into force-kill.

Grant `host.app.close` only for the exact opaque process resource:

```text
host-automation:host:<host-id>/process:<process-id>
```

When deployment policy requires host-level close confirmation, configure an explicit
`HostAutomationApprovalGate` and set
`host_automation_require_application_close_approval=True`. The Runtime composition
must reject that flag when no approval gate is supplied.

For model-originated close, keep normal RFC-0027 action-bound tool approval independent
from the host-service approval gate. Neither approval replaces fresh current
`tool.invoke` or `host.app.close` authorization.

Verify that changing the host epoch, application identity, process identity, operation,
or normalized arguments invalidates approval evidence. Close one disposable canary
application and confirm no arbitrary process termination path exists.

## Stage 8: enable clipboard write before considering read

Clipboard access is text-only in v0.32.0.

`host.clipboard.write` and `host.clipboard.read` are independent actions over:

```text
host-automation:host:<host-id>/clipboard:text
```

Start with write only. Write one deterministic non-sensitive canary string and verify
character/byte limits and operation timeout behavior.

Keep `clipboard_read_enabled=False` unless the deployment has explicitly reviewed the
sensitive-data disclosure risk. Granting `host.clipboard.read` policy while adapter
read remains disabled must not silently enable disclosure.

If read is required, enable it separately and verify bounded text-only results.
Clipboard text remains sensitive untrusted data: it cannot become a system message,
approval, credential, or Phoenix authority, and it must not appear in routine logs,
metrics, health payloads, audit payload text, or public error bodies.

File lists, images, HTML, rich text, arbitrary binary formats, and executable clipboard
objects remain outside the v0.32.0 surface.

## Stage 9: expose model-facing host tools separately

Do not let a model call `HostAutomationAdapter` or `HostAutomationService` directly.

Expose only reviewed RFC-0027 descriptors, resolvers, and adapters for the exact host
operations the agent needs. Tool IDs use the same narrow action names:

```text
host.process.list
host.window.list
host.app.launch
host.window.focus
host.app.close
host.clipboard.write
host.clipboard.read
```

For every model-originated operation, `tool.invoke` and `host.*` authorization remain
independent. The normal tool boundary validates the strict schema and resolves a
server-owned resource first; the host service then performs fresh exact host
authorization and host-specific validation/approval.

Do not let model output invent a host, configured application profile, executable
path, policy resource, native PID/HWND, approval, or broader tool schema.

## Stage 10: inspect content-free health, administration, and lifecycle

With host automation configured, Runtime owns the host boundary and exposes the
Runtime-owned services `host`, `host.health`, and `host.administration`.

Inspect the host service snapshot and operational surfaces. They may expose reviewed
Phoenix IDs, action names, finite limits, availability, bounded counts, durations, and
safe reason codes. They must exclude window-title text, clipboard text, executable
paths, command lines, environment variables, native handles, raw OS errors, approval
evidence, secrets, and credentials.

Exercise Runtime shutdown and restart. Shutdown must stop admitting new host effects,
allow bounded in-flight lifecycle handling, and close the adapter in Runtime-owned
order. A new adapter session gets a new finite host epoch so stale process/window
references cannot survive as authority.

## Stage 11: exercise cancellation, timeout, and indeterminate outcomes

Exercise cancellation before effect admission and operation timeout for the canary
surface.

Verify that:

- cancellation before a host effect begins prevents the new effect;
- cancellation after an operating-system effect begins does not fabricate rollback;
- launch, focus, close, and clipboard side effects are not transparently retried;
- an uncertain admitted effect is reported as indeterminate when Phoenix cannot know
  whether the operating-system-visible effect occurred;
- durable recovery does not transparently replay an indeterminate host side effect;
- read-only discovery failure does not widen authority or trigger a host mutation.

Operator recovery must re-observe current desktop state and obtain fresh current
authority instead of replaying a stale effect request.

## Rollback procedure

Use disable-first rollback.

1. Stop admitting new model-facing host tool calls.
2. Revoke `host.*` policy grants and any corresponding model-facing `tool.invoke`
   grants.
3. Remove the host-automation adapter and all host-specific options from Runtime
   composition.
4. Restart Phoenix and confirm `host`, `host.health`, and `host.administration` are
   absent and no desktop/clipboard probe occurs.
5. Keep shell, PowerShell, keyboard, mouse, arbitrary process termination, privilege
   elevation, and administrator automation disabled; do not use them as a substitute
   for the removed boundary.
6. Record any host effect whose outcome was indeterminate; do not replay it merely
   because the Runtime restarted.
7. Reinstall the recorded v0.31.0 package only when package rollback is required.

A package downgrade is not a host-effect rollback mechanism. Already admitted external
effects such as a launched application, changed focus, graceful close request, or
clipboard mutation are not guaranteed to be undone by replacing the Phoenix package.

## Release validation note

Gate 3 adds migration guidance and its regression test only. The named host-automation
release gate remains the next formal Slice 7 gate; this migration change does not
create or claim that gate.

For Gate 3 validation, run the existing repository quality suite:

```text
.\scripts\check.ps1
```

The later named host-automation release gate, Windows dogfood, offline wheel/sdist
validation, release notes, package version 0.32.0, tag, artifacts, and checksums remain
separate later Slice 7 work.
