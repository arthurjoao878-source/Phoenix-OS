# Migrating from Phoenix OS v0.30.0 to v0.31.0 agent workspaces

Phoenix OS v0.31.0 introduces the optional RFC-0031 secure agent-workspace and
artifact-handling subsystem. The safe first upgrade keeps workspace configuration
absent.

Files carry data, never authority. Installing or enabling workspaces does not grant
`workspace.list`, `workspace.read`, `workspace.write`, `workspace.delete`,
`workspace.import`, `workspace.export`, or `workspace.admin`; does not create an
artifact; does not mount a host directory; and does not turn file content, names,
metadata, provenance, approvals, credentials, or remembered instructions into
Phoenix authority.

## Compatibility baseline

When workspace configuration is omitted:

- no workspace store, backing adapter, local root, cleanup worker, recovery pass,
  transfer worker, transfer adapter, artifact context block, observer, or
  administration service is created;
- no principal receives any workspace action automatically;
- no prompt, response, tool result, memory record, child result, conversation,
  checkpoint, chain-of-thought, or hidden reasoning is captured automatically;
- Phoenix does not import, mount, scan, reinterpret, or copy existing host files,
  home directories, Downloads, Desktop folders, project trees, or v0.30 memory into
  artifacts;
- existing v0.30 agent, durable-agent, multi-agent, memory, model, tool, policy,
  approval, secret, network, persistence, Control Plane, and Runtime behavior remains
  unchanged.

This is a migration-free-by-omission upgrade. The disabled configuration is the first
upgrade checkpoint and the fastest disable-first rollback point.

## Pre-upgrade inventory

Record:

1. the exact v0.30.0 package and rollback artifact;
2. current agent, durable-agent, multi-agent, and memory configuration;
3. each agent that should receive an explicit workspace;
4. whether each intended scope is `run`, `agent`, or `principal`;
5. every proposed exact workspace policy edge;
6. artifact bytes, path, metadata, provenance, count, total-byte, retention,
   tombstone, recovery, cleanup, and administration bounds;
7. whether the confined local reference backing is sufficient;
8. any proposed external import/export adapter and the authority it needs outside
   Phoenix;
9. transfer queue, operation deadline, settlement, privacy, and data-residency
   requirements;
10. authoritative State Store and workspace-backing backup/restore procedures;
11. a rollback owner and maximum canary window.

Do not point the first v0.31 workspace canary at an existing arbitrary project,
personal, home, Downloads, or Desktop directory.

## Stage 1: install with workspace configuration absent

Install v0.31.0 while preserving the v0.30 configuration and do not create an
RFC-0031 workspace stack.

Confirm that no workspace root, artifact, store, backing object, cleanup/recovery
task, transfer worker, observer, administration service, or artifact context appears
merely because the package imports.

Confirm that v0.30 memory remains memory. Existing memory records, prompts, responses,
tool results, checkpoints, and host files must not be converted into artifacts.

## Stage 2: define one server-owned namespace and scope

Start with one reviewed agent and one `agent` scope.

Scope identity must be Phoenix-owned. Model output may propose data but cannot choose
an arbitrary namespace, agent, principal, run, or policy resource.

Verify the exact collection resource:

```text
agent-workspace:<namespace>/scope:<scope-kind>:<scope-id>
```

and direct artifact resource:

```text
agent-workspace:<namespace>/scope:<scope-kind>:<scope-id>/artifact:<artifact-id>
```

Do not create a global shared workspace. Parent and child agents do not share
workspaces by default.

## Stage 3: grant exact independent workspace policy

Grant only the operations required for the canary:

```text
workspace.list
workspace.read
workspace.write
workspace.delete
workspace.import
workspace.export
workspace.admin
```

Each action is independent. Do not infer workspace permission from `agent.run`,
`model.infer`, `tool.invoke`, `agent.delegate`, `agent.resume`, `agent.reconcile`,
`memory.*`, another workspace action, or historical artifact metadata.

Verify that revoking current workspace policy immediately wins over stored content,
filenames, provenance, prior grants, or approval-like text.

## Stage 4: keep logical paths separate from host paths

Use Phoenix logical paths as portable relative identifiers, not native host filesystem
paths.

Reject traversal, absolute paths, drive/UNC/device forms, NUL, empty/dot segments, and
ambiguous aliases. Do not let model output select a native backing path.

If the local reference adapter is used, dedicate one new Phoenix-owned absolute root.
Do not reuse a user's project tree or personal directory. Verify that link or special
filesystem objects and root escapes fail closed.

## Stage 5: start with conservative finite limits

Choose reviewed values below global ceilings for:

- artifact content bytes;
- logical-path length, segments, and segment length;
- metadata/provenance items, keys, values, and depth;
- artifacts and total bytes per scope;
- artifact TTL and tombstone retention;
- list/context item and byte limits;
- recovery and cleanup records/scopes per cycle;
- administration record limits and operation timeout;
- transfer worker count, queue capacity, operation timeout, and settlement timeout
  when transfers are installed.

Reject unlimited configuration.

## Stage 6: admit explicit writes only

Write one deterministic non-sensitive canary artifact.

Verify that:

- the write is an explicit server-admitted operation;
- the artifact has one Phoenix-owned `ArtifactId`;
- logical path, provenance, metadata, digest, version, and byte length are bounded;
- provenance describes origin but grants no trust or authority;
- normal conversation does not create a second artifact;
- chain-of-thought or hidden reasoning is never persisted;
- secret values and secret wrappers are not treated as ordinary artifacts;
- failed or cancelled writes do not become visible as committed artifacts.

## Stage 7: validate quota, version, and scope isolation

Exercise optimistic update/delete with the exact expected version.

Verify that stale mutations fail explicitly, canonical logical-path collisions are
rejected, concurrent quota races have at most one authoritative winner, and deleted
artifact IDs cannot be reused to resurrect old state.

Attempt the same `ArtifactId` from another run, agent, or principal scope.
Cross-namespace, cross-scope, and cross-artifact substitution must fail closed.

## Stage 8: validate explicit import and export separately

Keep transfer adapters absent for the first storage canary.

If external transfer is required, install one reviewed provider-neutral
`WorkspaceTransferAdapter`. Import and export remain independent operations with
independent exact authorization.

Verify that:

- a source reference cannot widen the server-owned workspace scope;
- import does not choose an arbitrary native destination path;
- artifact bytes or instructions cannot choose their own export destination;
- workspace read does not perform an implicit remote network fetch;
- imported bytes still pass normal workspace write, quota, digest, provenance, and
  version admission;
- exported bytes come only from freshly authorized authoritative artifact state;
- provider SDK objects, file handles, sockets, credentials, raw bodies, and raw
  provider exceptions remain behind the adapter boundary.

## Stage 9: validate untrusted artifact context

Opt one reviewed artifact into one agent run.

Verify that the context is bounded, provenance-preserving, and labeled untrusted
artifact data. It must enter model input as data, never as a system or policy message.

Binary artifacts are never silently decoded. Text decoding failures fail closed
unless a separate reviewed transform is explicitly installed outside the core
workspace contract.

Store a prompt-injection canary and verify that it cannot grant a model, tool,
approval, delegation, memory, import, export, credential, shell, network, browser,
desktop, host-filesystem, or other operating-system permission.

## Stage 10: run restart, corruption, and anti-resurrection canaries

Restart with active, expired, and deleted artifacts.

Verify that:

- only current active authoritative records can disclose backing bytes;
- deleted and expired artifacts remain absent;
- missing backing objects and digest substitutions fail closed;
- corrupt schema, identity-ledger loss, scope substitution, path collision, invalid
  provenance, and inconsistent authoritative metadata fail closed;
- recovery work is finite and reports content-free counters;
- failed startup self-cleans the Runtime-owned workspace boundary before propagating
  failure.

## Stage 11: inspect bounded lifecycle and safe operations

Exercise cleanup cancellation, transfer timeout/queue exhaustion when transfers are
installed, administration timeout, Runtime cancellation, and shutdown.

Review events, logs, metrics, health, recovery, and administration. They may expose
stable content-free IDs, scope categories, versions, counts, byte totals, status,
expiry categories, and fixed reason codes. They must exclude artifact bytes, decoded
text, logical/native host paths, credentials, approvals, secret material, provider
bodies, and raw exceptions.

## Rollback procedure

Use disable-first rollback.

1. Stop new workspace admission and remove Runtime workspace configuration.
2. Stop/restart Phoenix so no workspace store wrapper, cleanup worker, transfer
   worker, artifact-context provider, or administration service is active.
3. Remove workspace policy grants.
4. Preserve authoritative state and backing data if rollback may later be reversed.
5. Do not copy artifact bytes into agent prompts manually as a substitute for the
   disabled workspace boundary.
6. Reinstall the recorded v0.30.0 package only when package rollback is required.
7. Do not let a v0.30 process mutate storage reserved for v0.31 workspace semantics.

A package downgrade is not a workspace-artifact migrator.

## Release validation note

Slice 5A establishes architecture, migration, and threat-model evidence only. The
named agent-workspace release gate, offline wheel/sdist validation, release metadata,
version bump, final RFC acceptance, tag, artifacts, and checksums remain separate
later Slice 5 work and must pass before v0.31.0 publication.
