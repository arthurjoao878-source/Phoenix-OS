# Migrating from Phoenix OS v0.28.0 to v0.29.0 multi-agent coordination

Phoenix OS v0.29.0 introduces the optional RFC-0029 secure multi-agent coordination
subsystem. The safe first upgrade keeps coordination absent.

Delegation creates work, never authority. Installing or enabling coordination does
not copy a parent's permission, approval, credential, model grant, tool grant, or
policy decision into a child.

## Compatibility baseline

When coordination configuration is omitted:

- no delegable-agent registry entry is created automatically;
- no delegation, child run, coordination queue, worker, durable coordination store,
  recovery pass, event, or administration service is created;
- no principal receives `agent.delegate` automatically;
- RFC-0027 agent execution and RFC-0028 durable-agent execution remain independently
  configurable;
- existing v0.28 Control Plane, Dashboard, identity, service-account, webhook,
  inbound-event, inference, agent, durable-agent, workflow, job, audit, secret,
  Event Bus, network, TLS, and persistence behavior remains unchanged.

This disabled configuration is the first upgrade checkpoint and the fastest rollback
point.

## Pre-upgrade inventory

Record:

1. the exact v0.28.0 package and rollback artifact;
2. current RFC-0027 agent and RFC-0028 durable-agent configuration;
3. the exact parent agents that may delegate;
4. the reviewed child agent configurations that may be registered;
5. each proposed `agent.delegate` policy edge;
6. initial depth, fan-out, total-child, concurrency, queue, deadline, input/result,
   and aggregation limits;
7. the root budget ceiling and intended child reservation policy;
8. whether durable coordination is required;
9. the durable coordination database path/namespace and backup procedure if used;
10. a rollback owner and maximum canary window.

Do not point a first v0.29 durable-coordination canary at the only copy of production
coordination metadata.

## Stage 1: install with coordination absent

Install v0.29.0 while preserving the v0.28 configuration and do not create an
RFC-0029 coordination stack.

Confirm that no delegation resource, child run, queue, durable coordination file,
recovery pass, or coordination event appears merely because the package imports.

## Stage 2: register one reviewed child

Use one parent and one child. Registration is server-owned; the model must not choose
arbitrary executable child code.

Verify the child descriptor's exact:

- `AgentId`;
- namespace;
- reviewed `AgentServiceConfiguration`;
- allowed parent agents;
- maximum accepted depth;
- delegation limits;
- compatibility digest;
- nested-delegation setting.

A removed or materially changed child must fail current admission/recovery closed.

## Stage 3: grant exact delegation policy

Grant only the concrete edge:

```text
action: agent.delegate
resource: agent-delegation:<namespace>/parent:<parent-agent-id>/child:<child-agent-id>
```

Do not infer delegation permission from `agent.run`, `model.infer`, `tool.invoke`,
`agent.resume`, or `agent.reconcile`.

Verify that the child still receives independent current run/model/tool authorization
and that parent permissions, approvals, and credentials are not copied.

## Stage 4: start with conservative finite limits

Choose values below global ceilings for:

- maximum delegation depth;
- per-parent fan-out;
- total children per root;
- concurrent children;
- queued children;
- child timeout/deadline;
- child input bytes;
- result bytes and structured depth;
- aggregate result count/bytes;
- root model/tool/token/byte/duration budget.

Completing a child may free concurrency but must not restore lifetime root budget,
total-child capacity, or historical fan-out.

## Stage 5: validate lineage and result binding

Exercise a deterministic nested canary without external side effects.

Verify that:

- lineage is Phoenix-owned;
- cycles are rejected;
- nested delegation requires remaining depth and current policy;
- one `DelegationId` maps to one child run;
- a result from another child run is rejected;
- child output remains untrusted data;
- aggregation order and bounds are deterministic.

## Stage 6: validate cancellation and shutdown

Cancel a parent with queued and running children.

Confirm:

- no new child is admitted after parent cancellation;
- queued children are cancelled before later admission;
- running owned children receive cancellation;
- no detached child survives in v1;
- shutdown stops admission first and finishes within configured grace.

## Stage 7: enable durable coordination only when required

Start durable coordination with a fresh empty reference database.

Validate create/read/CAS behavior before executing a child. The durable record must
contain only content-free identity, budget, lifecycle, digest, compatibility, and
timestamp metadata. It must not contain raw child input, prompt, child output,
credentials, approval evidence, or provider response content.

The `DelegationId` to child-run binding is persisted before execution.

## Stage 8: run restart recovery canaries

Exercise three controlled crash windows:

1. child admitted but not started;
2. child persisted as running with outcome unknown;
3. terminal child followed by restart and a new delegation request.

Verify that:

- recoverable work reuses the exact persisted child run;
- two recoverers cannot both claim the same recoverable delegation;
- a running child becomes `INDETERMINATE` and is not replayed automatically;
- only reviewed evidence may confirm `NOT_STARTED` and permit the same child identity
  to resume;
- terminal child records still count against lifetime root budget, total children,
  and parent fan-out after restart;
- an indeterminate sibling blocks new/resumed work for that root.

## Stage 9: inspect safe operations

Review logs, metrics, audit, events, health, and administration.

They may expose stable content-free coordination identifiers, lifecycle categories,
bounded counts, durations, safe error codes, and approved digests. They must exclude
prompts, child input/output, raw results, credentials, approvals, secret references,
provider objects, external response bodies, and raw exceptions.

## Rollback procedure

Disable new coordination admission first.

1. Remove or disable Runtime coordination composition.
2. Stop new `agent.delegate` admission.
3. Let already admitted bounded children drain or cancel within configured grace.
4. Preserve durable coordination records that still contain recoverable or
   indeterminate work.
5. Reconcile indeterminate work with reviewed evidence; do not retry it merely to
   make rollback easier.
6. Remove coordination policy and registry configuration.
7. Restart Phoenix in the previous non-coordination v0.28-compatible configuration.
8. Reinstall the recorded v0.28.0 package only when package rollback is required.

A package downgrade is not a coordination-record migrator. Do not let a v0.28
process mutate a v0.29 durable coordination database.

## Release and package validation

Before publication run the full project gate and all named subsystem gates, ending
with:

```text
python scripts/check_multi_agent_release.py
```

The multi-agent gate validates RFC-0029 regression, migration, ADR, threat-review,
release, packaging, archive safety, and isolated package smoke suites. It builds
wheel and sdist, rebuilds a wheel from the validated sdist, and installs both wheel
forms with `--no-deps --no-index` in isolated environments without source-tree
imports.

## Final rollout checklist

- [ ] v0.28.0 baseline and rollback artifact recorded
- [ ] v0.29.0 starts with coordination configuration absent
- [ ] one reviewed parent/child edge registered
- [ ] exact `agent.delegate` policy tested
- [ ] conservative depth/fan-out/concurrency/queue/deadline limits tested
- [ ] root lifetime budget does not reset after completion
- [ ] Phoenix-owned lineage and cycle rejection tested
- [ ] child result substitution and aggregation bounds tested
- [ ] parent cancellation and finite shutdown tested
- [ ] durable child identity survives restart when durability is enabled
- [ ] running-at-crash child remains indeterminate until reconciled
- [ ] restart does not restore lifetime root budget or child capacity
- [ ] content-free operational surfaces reviewed
- [ ] disable-first rollback procedure rehearsed
- [ ] full quality and isolated package gates pass
