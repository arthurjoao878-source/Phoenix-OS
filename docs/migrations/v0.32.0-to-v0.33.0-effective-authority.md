# Migrating Phoenix OS 0.32.0 to 0.33.0

Phoenix OS 0.33.0 adopts RFC-0033 effective-authority and capability
non-amplification semantics across the already supported agent, tool, durable,
coordination, memory, workspace, host-automation, inference, identity, and
operator-control surfaces.

## Compatibility

The upgrade does not grant new operational authority. Existing canonical
subsystem authorizers remain authoritative and the authority inspection layer is
read-only. Effective authority is an intersection of the currently valid
subject, policy, approval, resource-freshness, cancellation, delegation, and
canonical-boundary constraints.

Deployments that construct session-backed `SecurityContext` values must preserve
the structural `session_id`. Attribute-derived session identifiers do not create
or preserve session authority. Agent and run identity must likewise remain
Phoenix-owned structural state rather than data recovered from prompts, memory,
workspace artifacts, tool output, or other untrusted content.

## Rollout

1. Upgrade code and package metadata without changing policy grants.
2. Run the complete regression suite and `python scripts/check_authority_release.py`.
3. Verify session-backed callers preserve structural session identity.
4. Verify approval flows bind the exact current subject, intent, and resource.
5. Verify composed agent/tool/memory/workspace/host paths still reach their
   canonical downstream authorizers.
6. Enable operator authority inspection only for principals that already hold
   the dedicated inspection/explanation permissions.

Authority inspection and explanation are point-in-time diagnostics. Their
responses are redacted data and must never be replayed as bearer authority.

## Operational checks

A failed current authority check is a security denial, not a reason to fall back
to an internal service identity or a historical grant. Unknown in-scope
protected operations fail closed under the closed-world authority catalog.

After any user- or attacker-controlled wait, revalidate revocable subject state,
resource identity/generation, cancellation, and the exact canonical admission
conditions before the protected effect.

## Rollback

Rollback to 0.32.0 is code/configuration rollback only. Do not transform an
RFC-0033 denial into an allow in order to preserve compatibility. Keep new
policy grants disabled, stop using the authority CLI, and restore the prior
application package. Durable data remains governed by its original subsystem
contracts; inspection output is non-authoritative and needs no migration.
