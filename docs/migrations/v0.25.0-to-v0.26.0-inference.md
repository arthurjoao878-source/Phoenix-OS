# Migrating from Phoenix OS v0.25.0 to v0.26.0 inference

This guide covers the opt-in secure model-provider and inference Runtime
introduced for Phoenix OS v0.26.0. It is intended for deployments that already
run v0.25.0 Control Plane, inbound events, webhooks, service accounts, sessions,
jobs, workflows, audit, secrets, Event Bus, plugins, or persistence.

The migration is additive. No provider, model, endpoint, secret reference,
policy grant, network permission, invocation, prompt, response, or persistent
content is created automatically. Existing service accounts receive no
inference scope or resource automatically.

## Compatibility boundary

`RuntimeAssembler` keeps inference absent unless `inference_enabled=True` is
supplied. A v0.25.0 assembly can be upgraded without adding inference arguments
and should preserve its previous service map, component order, Control Plane,
Dashboard, inbound-event, webhook, service-account, session, jobs, workflows,
audit, secrets, Event Bus, network, TLS, and persistence behavior.

Do not pass inference configuration, provider adapters, or machine-
administration options while `inference_enabled=False`. Phoenix rejects that
ambiguous state rather than retaining dormant security-sensitive configuration.

When inference configuration is omitted:

- no `inference` service or component exists;
- no provider or model is registered;
- no provider endpoint is resolved;
- no credential lease is acquired;
- no model request can be admitted;
- no Control Plane inference route is available;
- no inference State Store key is created;
- no prompt or response is persisted.

## Before upgrading

Complete these checks before enabling a provider:

1. Run the v0.25.0 quality gate and record the baseline.
2. Inventory each provider adapter and model that is genuinely required.
3. Review stable Phoenix provider and model identifiers separately from any
   provider-private model name.
4. Define finite message, input, output-token, response, chunk, deadline,
   first-byte, duration, and concurrency limits.
5. Define exact central-policy principals for `model.infer`.
6. Provision exact immutable credential versions through `SecretRef` when a
   provider requires authentication.
7. Review hosted HTTPS or explicit loopback-local endpoint policy.
8. Decide whether human administration, service-account administration, or
   neither is required.
9. Prepare rollback by removing invocation authority and disabling
   registrations before removing Runtime composition.
10. Confirm callers treat every model response as untrusted data.

Provider adapters are trusted installed code, not hostile-code sandboxes. Review
their dependency, transport, credential, cancellation, and output behavior
before installation.

## Step 1: upgrade with inference omitted

Upgrade the package or checked-out source while leaving the existing
`RuntimeAssembler` call unchanged. Validate the unchanged assembly first:

```powershell
python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pytest -q
```

Start and stop the application once without inference arguments. Verify that
`inference`, `inference.runtime`, `inference.registry`,
`inference.administration`, and `inference.health` are absent from the Runtime
service map.

This deployment proves v0.25.0 compatibility before any provider, credential,
network destination, or model authority is introduced.

## Step 2: validate contracts with the deterministic fake provider

Use `DeterministicModelProvider` first. It performs no network request and
requires no paid provider usage or credential.

```python
from phoenix_os.inference import (
    DeterministicModelProvider,
    InferenceProviderConfiguration,
    InferenceServiceConfiguration,
    ModelCapabilities,
    ModelDescriptor,
    ModelId,
    ModelProviderId,
)

provider_id = ModelProviderId("migration-fake")
model_id = ModelId("chat")

inference_configuration = InferenceServiceConfiguration(
    providers=(
        InferenceProviderConfiguration(provider_id),
    ),
    models=(
        ModelDescriptor(
            provider_id=provider_id,
            model_id=model_id,
            provider_model_name="chat",
            capabilities=ModelCapabilities(
                complete=True,
                streaming=True,
            ),
        ),
    ),
)

inference_providers = (
    DeterministicModelProvider(
        {"chat": "controlled migration response"},
        provider_id=provider_id,
    ),
)
```

Validate complete responses, streaming order, exactly one terminal record,
deadline handling, cancellation, malformed output rejection, and admission
limits before introducing a hosted or local model adapter.

The deterministic provider is for tests and controlled migration validation. It
does not prove that a third-party transport adapter is safe.

## Step 3: review provider and model registration

Every provider and model is registered from trusted server-side configuration.
The registry is the allowlisting boundary.

Review:

- stable `ModelProviderId` and `ModelId` values;
- exact installed adapter identity;
- provider/model capability compatibility;
- provider-private model aliases held only in trusted configuration;
- finite per-model `InferenceLimits`;
- finite global, provider, and model admission limits;
- explicit endpoint and credential policy;
- duplicate and configuration-mismatch rejection.

Callers select only registered identifiers. They cannot supply an endpoint,
credential, proxy, DNS resolver, TLS policy, arbitrary header, provider account,
or unregistered remote model.

Do not copy remote provider model discovery results directly into production
configuration. Treat model registration as a reviewed code/configuration change.

## Step 4: grant exact invocation authority

Every invocation requires the exact action:

```text
model.infer
```

The concrete resource form is:

```text
model-provider:<provider-id>/model:<model-id>
```

Create one central policy rule per reviewed principal and resource set. Avoid
wildcard provider or model grants during migration.

Inference authorization only permits one bounded request to reach the selected
provider/model registration. It never grants capability, command, job,
workflow, plugin, webhook, inbound-event, filesystem, shell, network, or
operating-system authority.

Model output is untrusted data. Text or structured output that resembles an
instruction, policy, identity, command, path, URL, or tool request requires a
new independent policy decision in the subsystem that would act on it.

## Step 5: provision exact credentials and endpoint policy

Provider credentials use an exact immutable `SecretRef` version. Store only the
reference in inference configuration.

```python
from phoenix_os.secrets import SecretRef

provider_credential = SecretRef(
    "provider-credential",
    "inference",
    7,
)
```

The plaintext value must not be printed, logged, placed in source control,
embedded in a request, returned by administration, or persisted in ordinary
configuration.

The inference Runtime leases the exact version immediately before adapter
execution and revokes the lease after completion, failure, timeout, or
cancellation. The central secret policy must permit only the required lease and
revocation operations for the inference service identity.

Hosted endpoints require reviewed HTTPS configuration, certificate
verification, explicit destination admission, bounded timeouts, pinned resolved
addresses, disabled ambient proxies, and disabled redirects. Every DNS answer
must satisfy the destination policy.

Plain HTTP is permitted only for an explicitly configured loopback-local
provider when every resolved address is loopback. Enabling a local provider does
not create or bind a second Phoenix listener.

Requests cannot change scheme, authority, port, path prefix, Host, proxy, DNS,
certificate, TLS, redirect, or credential destination policy.

## Step 6: enable the Runtime with reviewed registrations

After fake-provider validation, enable the Runtime with an exact configuration,
installed provider tuple, and central `PolicyEngine`:

```python
assembler = RuntimeAssembler(
    kernel=kernel,
    events=events,
    capabilities=capabilities,
    configuration=configuration,
    policy=policy,
    secrets=secrets,
    audit=audit,
    observability=observability,
    inference_enabled=True,
    inference_configuration=inference_configuration,
    inference_providers=inference_providers,
)
```

`SecretsManager` is required only when configured providers use credential
policies. Startup validates that installed provider identities exactly match
configuration and that provider/model capabilities are compatible before the
service is exposed.

The Runtime-owned services are:

```text
inference
inference.runtime
inference.registry
inference.administration
inference.health
```

Inference creates no background network listener. Provider adapters initiate
only the outbound or loopback connections admitted by their reviewed endpoint
policy.

## Step 7: inspect content-free health and inventory

Before any production invocation, inspect the administration snapshot and
provider/model views.

Safe views may contain stable identifiers, lifecycle state, revision,
capabilities, finite limits, endpoint mode, credential-configured boolean,
active counts, completion categories, bounded timing, and bounded usage facts.

They must not contain:

- prompt or response text;
- system instructions or message content;
- credential values, authorization headers, or secret versions;
- endpoint URLs or resolved addresses;
- provider-private model names or metadata;
- raw provider errors, tracebacks, SDK objects, or streaming frames.

Audit, logs, metrics, health, Dashboard, and Event Bus lifecycle events are
content-free by default.

## Step 8: enable human administration conservatively

Durable operator mode exposes reviewed provider/model inventory and lifecycle
operations through the existing Control Plane and Dashboard.

Grant only required permissions:

```text
inference.health.read
inference.provider.read
inference.provider.disable
inference.provider.enable
inference.model.read
inference.model.disable
inference.model.enable
```

Browser mutations require durable-session CSRF protection. Enable operations
require action-bound recent step-up authentication. Disable remains
CSRF-protected without step-up so a Maintainer can stop provider or model use
quickly.

Lifecycle changes use `expected_revision` and fail on stale state. Registration,
endpoint, credential, and model-alias creation remain configuration changes
outside the Dashboard.

Do not grant `*` merely to simplify migration.

## Step 9: optionally enable scoped machine administration

Machine administration is a separate opt-in:

```python
inference_service_account_administration_enabled=True
```

It also requires:

- inference enabled;
- durable operator mode;
- service accounts enabled;
- a fixed secure `ControlPlaneNetworkPolicy`;
- a central `PolicyEngine`;
- RFC-0023 authentication, nonce, timestamp, replay, audit, and policy controls;
- an exact `inference.*` action scope;
- gateway resource `inference-machine`;
- the concrete target resource.

Concrete resources are:

```text
inference:runtime
model-provider:<provider-id>
model-provider:<provider-id>/model:<model-id>
```

Machine routes provide content-free health, exact provider lookup, exact model
lookup, and optimistic enable/disable transitions. They intentionally provide no
aggregate provider inventory, aggregate model inventory, provider creation,
model registration, credential management, or endpoint management.

Browser cookies, CSRF proofs, and human step-up proofs are invalid at machine
routes. Service-account administration does not grant `model.infer`, and
invocation authority does not grant administration.

## Step 10: run a conservative canary

Use one reviewed provider and one model with the smallest practical limits and
concurrency. Keep unrelated callers denied.

Run controlled cases for:

- one complete response;
- one successful stream with exactly one terminal record;
- caller cancellation;
- deadline before completion;
- first-byte timeout;
- response, chunk, token, and input limit rejection;
- global, provider, and model saturation;
- malformed or out-of-order stream rejection;
- provider rejection and transport failure;
- credential lease revocation after every outcome.

The Runtime performs no transparent retry after provider execution begins.
Provider calls may be billable or nondeterministic, so any caller retry must be
explicit and use a new reviewed decision.

Verify that prompt text, response text, credentials, endpoint details, raw
provider failures, and model-generated structured payloads do not appear in
audit, logs, metrics, health, Dashboard, Event Bus events, or persistent state.

## Recommended production rollout

Use this order:

1. Upgrade with inference omitted and verify unchanged v0.25.0 behavior.
2. Validate contracts and limits with `DeterministicModelProvider`.
3. Review the installed provider adapter and exact model registration.
4. Provision exact secret versions and central secret policy when required.
5. Validate hosted HTTPS or explicit loopback-local endpoint admission.
6. Add exact `model.infer` policy rules for one canary principal and model.
7. Enable the Runtime with one provider and one model.
8. Inspect content-free health and administrative views.
9. Run complete, streaming, timeout, cancellation, malformed-output, and
   saturation canaries.
10. Confirm every credential lease is revoked and no content leaks.
11. Enable human lifecycle administration only for required Maintainers.
12. Enable machine administration only after a separate security review.
13. Expand principals, providers, models, and concurrency gradually.
14. Keep automatic provider failover and transparent retry disabled.

## Rollback without losing unrelated state

Rollback should first remove inference authority, not delete unrelated Phoenix
state or provider credentials.

1. Remove or deny new `model.infer` policy grants.
2. Disable every active model using its current `expected_revision`.
3. Disable every active provider using its current `expected_revision`.
4. Confirm content-free health reports no newly admitted invocations.
5. Allow active invocations to complete within their finite deadlines, or invoke
   bounded shutdown cancellation and record the terminal categories.
6. Confirm admission capacity is released and credential leases are revoked.
7. Stop the Runtime.
8. Remove `inference_enabled`, `inference_configuration`,
   `inference_providers`, and
   `inference_service_account_administration_enabled` from the next assembly.
9. Preserve exact `SecretRef` versions and reviewed configuration until no
   deployment or rollback record relies on them.
10. Start the feature-disabled or downgraded deployment and verify that no
    `inference*` service or Control Plane route exists.
11. Verify inbound events, webhooks, service accounts, sessions, jobs,
    workflows, audit, secrets, Event Bus, network, TLS, and persistence remain
    unchanged.

Inference does not persist prompts or responses by default and creates no
inference State Store records. Do not add ad hoc prompt/response persistence as
part of rollback.

A package downgrade to v0.25.0 has no inference service to interpret. Keep
provider configuration and secret versions outside the downgraded Runtime until
a reviewed re-enable or retirement procedure is complete.

Do not revoke or delete credential versions while an active invocation, staged
configuration, audit record, or rollback plan still relies on the reference.

## Health and acceptance checks

After enabling the subsystem:

```python
service = runtime.service("inference")
administration = runtime.service("inference.administration")

runtime_snapshot = await service.snapshot()
administration_snapshot = await administration.snapshot(maintainer_context)
```

Verify:

- the Runtime state and `accepting` flag are expected;
- provider and model counts match reviewed configuration;
- enabled counts match lifecycle state;
- active, started, completed, rejected, failed, cancelled, timed-out, and forced
  cancellation counters match controlled cases;
- every stream has ordered chunks and exactly one terminal record;
- cancellation and shutdown complete within finite bounds;
- no credential lease remains after terminal outcomes;
- no endpoint, secret, prompt, response, provider-private metadata, raw error, or
  streaming frame appears in safe output;
- Dashboard and machine routes remain absent unless explicitly enabled;
- service-account scopes and concrete resources are exact;
- unrelated Phoenix services retain their prior behavior.

Run the complete project gate after the migration configuration is in place:

```powershell
python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pytest -q
```

The final v0.26.0 release gate must also build and inspect wheel and sdist
artifacts, rebuild a wheel from the validated sdist, install both wheels in
isolated offline environments, and exercise the packaged inference,
administration, limits, streaming, cancellation, and compatibility surfaces.

## Normative migration checks

Inference remains absent when inference configuration is omitted.

Model output receives no implicit Phoenix authority.

The final package gate installs both wheels in isolated offline environments.

## Migration invariants

The migration is complete only when all of these remain true:

- inference is disabled by default;
- no provider, model, endpoint, credential, or policy grant is created
  automatically;
- callers can select only reviewed registered identifiers;
- every invocation requires exact `model.infer` and a concrete model resource;
- model output remains untrusted data;
- exact credential versions are leased only during provider execution;
- hosted endpoints fail closed and loopback HTTP remains explicit;
- every input, output, stream, timeout, and concurrency dimension is finite;
- admission occurs before credential leasing or provider execution;
- streams require exactly one terminal record;
- cancellation and cleanup are bounded;
- no transparent retry occurs after provider execution begins;
- prompts, responses, credentials, endpoints, and raw provider errors remain
  outside safe output and ordinary persistence;
- human and machine administration remain separately authorized;
- rollback removes invocation authority before Runtime composition;
- unrelated Phoenix state survives enablement and rollback.
