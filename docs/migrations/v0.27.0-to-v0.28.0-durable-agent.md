# Migrating from Phoenix OS v0.27.0 to v0.28.0 durable agent runs

Phoenix OS v0.28.0 introduces the optional RFC-0028 durable-agent subsystem for
bounded checkpoints, restart recovery, fenced leases, controlled reconciliation,
retention, cleanup, and content-free administration.

The safe first upgrade is deliberately boring: install the v0.28.0 package while
keeping durable-agent configuration absent. Ordinary in-memory RFC-0027 agent
execution and independently configured RFC-0026 inference remain available.

Durability is not authority. A checkpoint is data, not authority, and cannot grant
permission, approval, a credential, a lease, or proof that external work completed.
No principal receives `agent.resume`, `agent.reconcile`, `agent.durable.cleanup`, or
durable read authority automatically.

## Compatibility baseline

When durable-agent configuration is omitted:

- no durable run, checkpoint, protected payload, lease, recovery worker, retention
  worker, cleanup pass, or durable administration service is created;
- no durable storage namespace is initialized merely because the package imports;
- no protected-payload key is leased;
- no durable permission, approval, model call, tool call, or external access is
  created;
- ordinary in-memory RFC-0027 agent execution remains available when configured;
- RFC-0026 inference remains independently configurable;
- existing Control Plane, Dashboard, service-account, webhook, inbound-event,
  session, job, workflow, audit, secret, Event Bus, network, TLS, and persistence
  behavior remains compatible with v0.27.0.

This disabled configuration is the first upgrade checkpoint and the fastest
disable-first rollback point.

## Pre-upgrade inventory

Before enabling durability, record:

1. the exact v0.27.0 package artifact and configuration revision;
2. the existing RFC-0027 agent, RFC-0026 inference, Policy Engine, approval, audit,
   Event Bus, and Runtime baselines;
3. State Store and Audit Store backups under the deployment's normal backup process;
4. the intended durable-store adapter, path or namespace, and filesystem ownership;
5. the checkpoint schema and codec versions that will be admitted;
6. the initial payload profile, beginning with `METADATA_ONLY`;
7. any proposed `PROTECTED_CONTENT` key references and their exact versions;
8. lease duration, renewal, recovery admission, queue, concurrency, and shutdown
   limits;
9. retention, payload-retention, tombstone, cleanup-page, and cleanup-duration
   limits;
10. exact human and machine principals proposed for durable administration;
11. exact `agent.resume`, `agent.reconcile`, read, health, and cleanup policy rules;
12. a rollback owner and a maximum acceptable canary window.

Do not point a v0.28.0 canary at the only copy of production durable data. Preserve
a rollback-safe backup and use a fresh empty namespace for the first deterministic
storage and codec validation.

## Stage 1: install with durability absent

Install v0.28.0 and start Phoenix with the same non-durable agent configuration
used by v0.27.0. Do not add durable-store, payload-protection, lease, recovery,
retention, cleanup, or durable-administration configuration yet.

Confirm:

- no durable Runtime service is exposed;
- no durable storage file or namespace is created by disabled configuration;
- no recovery or retention worker starts;
- no durable event or audit fact appears;
- no key lease is requested;
- ordinary RFC-0027 agent tests still behave as before;
- independently configured RFC-0026 inference still behaves as before.

Do not proceed merely because imports succeed.

## Stage 2: run deterministic storage and codec validation

Before model or tool work, validate the durable storage boundary with deterministic
network-free tests and a fresh empty namespace.

Exercise:

- create one durable run and first checkpoint;
- strict canonical checkpoint encoding and decoding;
- monotonic checkpoint sequence enforcement;
- optimistic run-version enforcement;
- cross-run checkpoint substitution rejection;
- digest-chain validation;
- malformed, oversized, duplicate-key, and unsupported-version rejection;
- lease acquisition and fenced mutation;
- lease expiry and reacquisition with a higher fencing generation;
- rejection of a stale fencing generation;
- terminal tombstone persistence and anti-resurrection behavior.

Checkpoint corruption, rollback, substitution, and unsupported versions fail closed.
A storage error with an unknown commit outcome must be resolved by an exact re-read
and version comparison, not by blindly repeating a mutation.

## Stage 3: enable a metadata-only durable canary

Begin with `METADATA_ONLY`. Do not enable protected content during the first canary.

The canary should persist only reviewed content-free checkpoint metadata. It must
not persist a prompt, model response, raw argument, tool result, credential, secret
reference, approval token, external response body, or raw exception.

Exercise a bounded run that reaches safe checkpoint boundaries and then restart the
Runtime. Verify that:

- recovery acquires a fresh fenced lease;
- the current checkpoint is re-read after lease acquisition;
- current configuration, registry, schemas, limits, and policy override persisted
  metadata;
- `agent.resume` receives a fresh exact authorization decision;
- resumed model turns still receive independent `model.infer` authorization;
- resumed tool calls still receive independent exact `tool.invoke` authorization;
- restart does not reset budgets or deadlines;
- completed model or tool attempts are not repeated;
- an attempt left active across process loss becomes indeterminate unless reviewed
  evidence proves a safe outcome.

There is no transparent retry of model turns or tool invocations.

## Stage 4: validate lease, fencing, compatibility, and recovery limits

Use conservative finite values below global ceilings.

Validate:

- one active lease holder per run;
- monotonically increasing fencing generations on acquisition;
- renewal without generation reuse or widening authority;
- stale-worker writes rejected after expiry or replacement;
- bounded recovery page size, queue depth, concurrency, attempts, and duration;
- bounded pause and total durable lifetime;
- checkpoint count, envelope bytes, history bytes, and protected-payload bytes;
- controlled shutdown within finite grace;
- deterministic startup rollback when a required durable dependency fails.

Test compatible and incompatible configuration changes. A removed model, removed
tool, changed effect class, incompatible schema, changed resolver, unsupported
checkpoint version, or unavailable protection key must fail recovery closed.

## Stage 5: configure exact policy and operator administration

Add durable authority explicitly and minimally.

Human operator administration should use authenticated durable operator sessions
and exact permissions. Destructive cleanup and reconciliation require exact
authorization, recent human step-up authentication, confirmation, and audit.

Machine administration remains disabled by default. If machine reads are enabled,
grant only exact service-account scopes and resources. Do not expose a machine
cleanup endpoint merely because machine reads are available.

Verify that wildcard permission does not satisfy exact destructive authority.

## Stage 6: validate approval waiting and reconciliation

Checkpointed approval correlation metadata is not approval authority. After restart,
query the trusted approval gate and validate the current exact approval state.

Verify expiration, denial, prior consumption, actor mismatch, invocation mutation,
and replay rejection.

For an indeterminate attempt, do not retry first. Reconciliation uses the exact
`agent.reconcile` action and the exact durable run plus attempt resource. A reviewed
disposition must remain bound to that attempt and cannot rewrite tool, resource,
argument, actor, or attempt identity.

When evidence is insufficient, keep the run indeterminate or terminate safely.

## Stage 7: enable protected content only when required

Enable `PROTECTED_CONTENT` only after the metadata-only canary passes and only when
reviewed continuation content is genuinely required.

Protected payloads require:

- authenticated encryption;
- bounded plaintext and ciphertext sizes;
- versioned secret references resolved through trusted composition;
- exact run, checkpoint, sequence, schema, and profile associated data;
- finite payload retention shorter than the deployment's reviewed
  metadata-retention policy;
- decryption only after authorization, lease acquisition, and checkpoint validation;
- fail-closed behavior for missing keys, revoked versions, invalid tags, or
  incompatible codecs.

Never log plaintext or ciphertext, payload storage paths, key material, key secret
references, or raw decryption exceptions.

Encryption does not replace authorization.

## Stage 8: configure retention, cleanup, and tombstones

Begin with retention limits that preserve enough content-free metadata to diagnose
the canary while keeping protected content retention short.

Validate that cleanup:

- uses bounded pages and a finite pass duration;
- derives bounds from trusted Runtime-owned retention configuration;
- skips actively leased runs;
- deletes protected payloads before or atomically with their references where
  supported;
- preserves terminal tombstones and anti-resurrection metadata;
- exposes only safe counters and categories;
- tolerates repeated execution without deleting active data.

Human destructive cleanup must remain step-up protected, confirmed, and audited.
Do not send client-selected candidate identifiers, fencing generations, retention
deadlines, payload references, or storage paths to the cleanup worker.

## Stage 9: inspect content-free observability

Review audit, metrics, logs, health, Event Bus events, and administration output.

Approved output may contain stable durable identifiers, checkpoint sequence, schema
version, fencing generation, state, safe pause or terminal categories, compatibility
categories, payload profile, bounded counts, ages, sizes, durations, and approved
digests.

It must exclude prompts, model responses, raw arguments, tool results, protected
payload plaintext or ciphertext, payload paths, credentials, secret references,
approval tokens, endpoint details, external response bodies, raw reconciliation
evidence, and raw exceptions.

Do not add temporary content logging to debug recovery.

## Stage 10: run the restart and rollback canary

Use one trusted principal and the smallest reviewed agent/tool set. During the
canary, verify:

- safe checkpoint creation before restart;
- recovery only from a reviewed safe boundary;
- fresh resume, model, and tool authorization counts;
- current fencing generation before every leased run or checkpoint mutation;
- no automatic repetition of an indeterminate model or tool attempt;
- exact reconciliation for deliberately constructed indeterminate fixtures;
- finite shutdown and recovery-worker drain;
- retention skips active leases;
- cleanup preserves terminal anti-resurrection state;
- safe observation remains content-free.

Do not use a live external side effect merely to prove that restart works.

## Rollback procedure

Disable new durable admission and automatic recovery first. Disabling durability
does not delete existing durable records automatically and does not disable
ordinary in-memory RFC-0027 agent execution or independently configured RFC-0026
inference.

1. Reject new durable admission.
2. Stop or pause automatic recovery admission.
3. Stop destructive cleanup admission.
4. Let already admitted bounded work drain within configured grace periods.
5. Preserve durable records for later compatible recovery.
6. Export only safe content-free diagnostics required for incident review.
7. For retained indeterminate runs, use explicit reviewed reconciliation or an
   explicitly authorized cancel/fail procedure rather than retrying work.
8. Delete protected payloads only through confirmed retention procedures.
9. Remove durable configuration and restart Phoenix in non-durable RFC-0027 mode.
10. Reinstall the recorded v0.27.0 package only when package rollback is necessary.

A package downgrade is not a checkpoint migrator. Do not let a downgraded v0.27.0
process write to a v0.28.0 durable namespace. Preserve that namespace offline or
under access controls until a compatible v0.28.0 process can inspect, reconcile,
retain, or clean it.

Rollback cannot prove that an external effect did not happen. An indeterminate
external attempt remains indeterminate until reviewed evidence resolves it.

## Release and package validation

Before release, run the full quality gate from a clean checkout:

```text
python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pytest -q
python scripts/check_webhook_release.py
python scripts/check_inbound_release.py
python scripts/check_inference_release.py
python scripts/check_agent_release.py
```

The final v0.28.0 agent release gate must include the RFC-0028 durable security,
migration, ADR, release, packaging, and isolated smoke suites. Wheel and sdist
artifacts must be inspected for unsafe paths and sensitive files, the wheel rebuilt
from the validated sdist, and both wheels installed with `--no-deps --no-index` in
isolated offline environments without source-tree imports.

- [ ] v0.28.0 starts with durable-agent configuration absent
- [ ] deterministic storage and codec validation passes
- [ ] metadata-only restart canary passes
- [ ] lease expiry and stale-fencing rejection pass
- [ ] current compatibility rules and stricter limits win after restart
- [ ] exact resume, model, tool, reconciliation, and cleanup policy tested
- [ ] approval replay and mutation tests pass after restart
- [ ] indeterminate attempts are never retried automatically
- [ ] protected payloads remain disabled unless explicitly required
- [ ] protected payload encryption, key-version failure, and retention tested when enabled
- [ ] retention skips active leases and preserves tombstones
- [ ] content-free audit and administration verified
