# Migrating from Phoenix OS v0.29.0 to v0.30.0 agent memory

Phoenix OS v0.30.0 introduces the optional RFC-0030 secure agent-memory and context
retrieval subsystem. The safe first upgrade keeps memory absent.

Memory informs work, never authority. Installing or enabling memory does not grant
`memory.search`, `memory.read`, `memory.write`, `memory.delete`, or `memory.admin`;
does not create a record; and does not turn remembered text into policy, approval,
credential, model, tool, delegation, resume, or reconciliation authority.

## Compatibility baseline

When memory configuration is omitted:

- no memory store, namespace registry, retrieval adapter, semantic index, embedding
  provider, cleanup/recovery worker, context block, event, or administration service
  is created;
- no principal receives any memory action automatically;
- no prompt, response, tool result, child result, checkpoint, or conversation is
  captured automatically;
- RFC-0027 agent, RFC-0028 durable-agent, and RFC-0029 multi-agent behavior remains
  unchanged;
- existing v0.29 Control Plane, Dashboard, identity, service-account, webhook,
  inbound-event, inference, workflow, job, audit, secret, Event Bus, network, TLS,
  and persistence behavior remains unchanged.

This disabled configuration is the first upgrade checkpoint and the fastest
disable-first rollback point.

## Pre-upgrade inventory

Record:

1. the exact v0.29.0 package and rollback artifact;
2. current agent, durable-agent, and multi-agent configuration;
3. each agent that should receive a memory namespace;
4. whether each intended scope is `run`, `agent`, or `principal`;
5. every proposed exact memory policy edge;
6. record-size, metadata, provenance, count, total-byte, query, result, context, TTL,
   and tombstone bounds;
7. whether deterministic lexical retrieval is sufficient;
8. whether an external semantic/embedding provider is proposed;
9. provider privacy, data-residency, and timeout requirements when semantic retrieval
   is used;
10. authoritative State Store backup/restore procedures;
11. a rollback owner and maximum canary window.

Do not point the first v0.30 memory canary at the only copy of production memory
state.

## Stage 1: install with memory absent

Install v0.30.0 while preserving the v0.29 configuration and do not create an
RFC-0030 memory stack.

Confirm that no memory resource, record, store, index, worker, recovery pass,
provider call, or retrieved context appears merely because the package imports.

## Stage 2: define one server-owned namespace and scope

Start with one reviewed agent and one `agent` scope.

Scope identity must be Phoenix-owned. Model output may propose content or a query but
must not choose an arbitrary namespace, agent, principal, run, or policy resource.

Verify the exact collection resource:

```text
agent-memory:<namespace>/scope:<scope-kind>:<scope-id>
```

and direct record resource:

```text
agent-memory:<namespace>/scope:<scope-kind>:<scope-id>/record:<memory-id>
```

Do not create a global shared scope. Parent and child agents do not share memory by
default.

## Stage 3: grant exact independent memory policy

Grant only the operations required for the canary:

```text
memory.search
memory.read
memory.write
memory.delete
memory.admin
```

Each action is independent. Do not infer memory permission from `agent.run`,
`model.infer`, `tool.invoke`, `agent.delegate`, `agent.resume`, or
`agent.reconcile`.

Verify that revoking current memory policy immediately wins over historical record
metadata or remembered instructions.

## Stage 4: start with conservative finite limits

Choose values below global ceilings for:

- record content bytes;
- metadata/provenance items, keys, values, and depth;
- records and total bytes per scope;
- record TTL and tombstone retention;
- search-query bytes;
- result count and returned bytes;
- context item count and bytes;
- semantic provider/index operation timeout;
- recovery/cleanup scopes and records per cycle.

Reject unlimited configuration.

## Stage 5: admit explicit writes only

Write one deterministic non-sensitive canary record.

Verify that:

- the write is an explicit server-admitted operation;
- the record has one Phoenix-owned `MemoryId`;
- provenance is immutable and bounded;
- content digest and logical version are present;
- normal conversation does not create a second record;
- chain-of-thought or hidden reasoning is never persisted;
- secrets and secret wrappers are not treated as ordinary memory.

## Stage 6: validate scope isolation

Attempt the same `MemoryId` from a different agent scope and principal scope.

Cross-namespace, cross-scope, and cross-record substitution must fail closed.
There is no implicit sharing across agent, principal, run, parent, or child scopes.

## Stage 7: validate retrieval and untrusted context

Search for the canary through the deterministic reference adapter.

Verify that:

- result count and bytes are bounded;
- scores are finite and validated;
- equal scores use deterministic Phoenix-owned tie-breaking;
- every candidate is re-read from the authoritative source;
- context preserves provenance;
- retrieved content is labeled untrusted and enters as data, never as system policy;
- prompt injection inside a record cannot grant a tool, model, approval, delegation,
  credential, or memory permission.

## Stage 8: enable semantic retrieval only when required

Keep semantic retrieval disabled for the first canary.

If a semantic provider is required, install it behind the provider-neutral
`MemoryEmbeddingProvider` boundary. Review what content/query text leaves Phoenix,
where it is processed, and its timeout/privacy policy.

The derived index may contain only candidate identity/version/digest plus vector
data. It is not record truth. Provider SDK objects do not enter Phoenix public
contracts or safe operational output.

## Stage 9: validate mutation, expiry, and anti-resurrection

Create, update with the exact expected version, then delete a canary.

Verify that:

- stale writes and deletes fail explicitly;
- delete creates authoritative absence/tombstone semantics;
- direct read and retrieval cannot return the tombstoned record;
- stale lexical/semantic candidates cannot resurrect it;
- expired records are absent from read, retrieval, context, and recovery.

## Stage 10: run restart and corruption canaries

Restart with authoritative records and rebuild any derived index.

Verify that:

- only active unexpired authoritative records are indexed;
- deleted/expired records do not reappear;
- wrong version/digest candidates are rejected;
- corrupt schema, substituted scope identity, invalid provenance, and inconsistent
  record identity fail closed;
- failed startup self-cleans the memory store/index wrapper before propagating the
  failure.

## Stage 11: inspect bounded lifecycle and safe operations

Exercise provider timeout, recovery timeout, maintenance cancellation, and Runtime
shutdown.

Review events, logs, metrics, health, and administration. They may expose stable
content-free IDs, scope categories, versions, counts, byte totals, status, expiry
categories, and fixed reason codes. They must exclude memory text, query text,
embeddings, credentials, approvals, secret material, provider bodies, and raw
exceptions.

## Rollback procedure

Use disable-first rollback.

1. Stop new memory admission and remove Runtime memory configuration.
2. Stop/restart Phoenix so no memory retrieval/index/cleanup worker is active.
3. Remove memory policy grants.
4. Preserve the authoritative store if rollback may later be reversed.
5. Do not copy records into agent prompts manually as a substitute for the disabled
   memory boundary.
6. Reinstall the recorded v0.29.0 package only when package rollback is required.
7. Do not let a v0.29 process mutate storage reserved for v0.30 memory semantics.

A package downgrade is not a memory-record migrator.

## Release and package validation

Before publication run the full project gate and all named subsystem gates, ending
with:

```text
python scripts/check_agent_memory_release.py
```

The agent-memory gate validates RFC-0030 regressions, migration, ADR, threat-review,
release metadata, package contents, archive safety, and isolated execution. It
builds wheel and sdist, rebuilds a wheel from the validated sdist, and installs both
wheel forms with `--no-deps --no-index` in isolated environments without source-tree
imports.
