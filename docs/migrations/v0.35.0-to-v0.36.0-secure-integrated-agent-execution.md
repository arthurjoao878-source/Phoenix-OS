# Migration: Phoenix OS v0.35.0 to v0.36.0 secure integrated agent execution

RFC-0036 adds an optional Phoenix-owned task-level orchestration layer that composes
existing agent, inference, memory, workspace, host, network, browser, and durable-run
boundaries without replacing their authority models.

## Compatibility default

No migration action is required to preserve Phoenix OS v0.35.0 behavior.

When integrated-execution configuration is omitted, Phoenix creates no integrated task,
profile, planner, additional tool surface, downstream bridge, data-flow route, durable
projection, observer, administration authority, worker, permission, approval, credential,
browser session, network request, host effect, memory operation, or workspace mutation.

Enabling integrated execution grants no authority automatically. Existing `agent.run`,
`model.infer`, `tool.invoke`, memory, workspace, host, network, browser, delegation, and
durable-run boundaries remain independently authoritative.

## Task and profile migration

Applications adopting integrated execution must create bounded `IntegratedTaskRequest`
values and configure immutable server-owned `IntegratedExecutionProfile` objects.

Every `IntegratedTaskId` is permanently bound to one canonical task digest. Reusing one
task identity with different task bytes or reviewed input references fails closed.

The exact integrated profile ID and positive generation are resolved from trusted
configured-agent state before `agent.run` authorization. Task or model text cannot choose
a stronger profile, profile generation, credential, policy resource, or downstream
binding.

Existing RFC-0027 `AgentRunId` and `AgentStepId` identities remain authoritative. There
is no `task.run` replacement authority and no second run/step identity system.

## Planning migration

Planning is advisory data.

The model still returns exactly final bounded output or one RFC-0027
`ToolCallProposal`. Plan updates use only the reserved server-owned
`integrated.plan.update` tool, cross normal `tool.invoke` authorization, and may mutate
only bounded advisory plan state for the exact task/run.

A plan does not become an executable RFC-0016 workflow graph, approval, credential,
profile selector, policy resource, or downstream authority.

## Tool composition migration

Every model-visible integrated tool must have exactly one immutable server-owned
`IntegratedToolBinding` and is classified as exactly one of:

```text
LOCAL_TRANSFORM
DOWNSTREAM_BRIDGE
```

Integrated execution reuses the existing RFC-0027 `ToolRegistry`; deployments must not
create a second integrated capability registry.

A local transform has no ambient filesystem, network, browser, host, memory, workspace,
secret, policy, Runtime, or adapter authority.

A downstream bridge is bound to one exact reviewed downstream boundary, action family,
profile/scope/resource identity, and applicable generation/freshness. The bridge must use
the canonical downstream Phoenix service and cannot substitute another profile,
namespace, scope, host target, resource, or action because it is available at runtime.

`tool.invoke` and downstream canonical authority remain independent requirements.

## Data-flow and provenance migration

Authority and disclosure are separate.

Integrated profiles must define finite server-owned data-flow routes for every admitted
cross-subsystem flow. A caller or model cannot manufacture a route through text.

Every integrated value retains bounded exact Phoenix-owned provenance atoms carrying
source kind, reviewed source binding, and applicable freshness. Model turns, local
transforms, bridge transformations, and planner normalization conservatively union all
input provenance plus the Phoenix-owned output source atom.

Phoenix OS v0.36.0 has no provenance declassification primitive. Provenance cannot be
removed, weakened, relabeled, silently coalesced, or truncated to satisfy a later route.
Atom-count or encoded-byte overflow fails closed before content is injected, stored,
passed, or disclosed.

Data-flow denial occurs before approval consumption and before downstream effect
admission. A data-flow allow grants no `tool.invoke` or downstream protected-operation
authority.

## Final-result disclosure

Final model output is not automatically releasable.

The final result crosses the explicit `USER_RESULT` sink. The result audience is derived
from trusted task admission and authenticated Phoenix context, never arbitrary model or
caller recipient text.

Any route to `USER_RESULT` must explicitly require and satisfy audience/source-scope
constraints. A denied route releases no protected content.

## Budgets, deadlines, cancellation, and effects

Integrated execution is finite and sequential in v0.36.0. At most one effectful
integrated step is admitted at a time per run.

Existing RFC-0027 limits remain authoritative. Integrated task-level limits compose by
minimum with all applicable subsystem limits. Child deadlines never extend the parent
remaining deadline and current cancellation prevents admission of new work.

Potentially effectful work is never transparently retried. If an authoritative downstream
boundary cannot prove completion or non-execution after an effect may have started, the
attempt is `INDETERMINATE` and automatic repetition is blocked.

## Durability and recovery

Durability remains optional and is implemented through RFC-0028.

Integrated persistence adds only bounded orchestration metadata such as exact task
identity/digest, integrated profile ID/generation, plan revision/digest, budget usage,
data-flow context digest, phase, safe-boundary metadata, and waiting reason.

Metadata-only recovery does not prove that planning context is reconstructable. If
sufficient reviewed context is unavailable, Phoenix waits for explicit reviewed context
resupply or terminates safely; it does not fabricate or silently replay missing content.

Recovery requires exact persisted task/profile compatibility, current configuration,
current tool surface, current downstream profiles, current policy/authority, current
limits/deadline/cancellation, current approvals where required, and current subsystem
freshness. Consumed approvals and stale browser identities are not restored.

An indeterminate external attempt enters the existing RFC-0028 reconciliation path and
is never automatically replayed.

## Observability and administration

Routine integrated observability, health, and administration are content-free.

Allowed operational metadata is limited to reviewed bounded identifiers and finite
state such as task/run/step IDs, plan revision, profile ID/generation, derived phase,
tool/capability identifiers, action category, effect disposition, failure class, budget
counters, duration, and waiting reason.

Routine surfaces exclude task text, prompts, model responses, tool arguments/results,
browser page text, raw network bodies, memory/workspace/clipboard content, cookies,
credentials, secrets, approval evidence, policy internals, and raw exceptions.

Read-only health requires `integrated.agent.health.read`. Separately authorized run
inspection requires `integrated.agent.inspection.read`; service-principal inspection is
bound to the exact run-scoped inspection resource. Inspection exposes only reviewed
bounded redacted metadata and never raw provenance source bindings or content.

## Release-gate adoption

Run the dedicated integrated-agent hardening gate in addition to the existing global
checks once S7e adds it:

```text
python scripts/check_integrated_agent_release.py
```

The gate must validate the frozen RFC-0036 authority, provenance, data-flow, recovery,
observability, package-boundary, isolated-install, and deterministic network-free E2E
requirements.

S7 intentionally does not change `pyproject.toml`, `CHANGELOG.md`,
`docs/releases/v0.36.0.md`, tags, publication metadata, or remote release state.
RFC-0036 S8 performs v0.36.0 release finalization only after S1-S7 targeted security,
global, package, canonical-diff, and adversarial gates are green.
