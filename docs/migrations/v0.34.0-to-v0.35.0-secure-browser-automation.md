# Migration: Phoenix OS v0.34.0 to v0.35.0 secure browser automation

RFC-0035 adds an opt-in secure browser-automation boundary. This guide describes the
configuration and security changes required to adopt it without widening existing
Phoenix authority.

## Compatibility default

No migration action is required to preserve Phoenix OS v0.34.0 behavior.

When browser-automation configuration is omitted, Phoenix creates no browser profile,
browser process, session, page, cookie jar, navigation, tool binding, network request,
host effect, workspace transfer, listener, worker, permission, or approval.

Enabling the subsystem grants no browser action automatically. Browser authority,
`tool.invoke`, `network.http.request`, host authority, workspace authority, memory
authority, and model authority remain independent and intersect only at reviewed
composition points.

## Server-owned configuration

Browser profiles are immutable server-owned configuration. Callers select stable
profile IDs and, where applicable, stable navigation-target IDs. They do not supply
arbitrary URLs, schemes, hosts, ports, proxies, selectors, XPath, coordinates,
JavaScript, executable paths, browser flags, cookies, credentials, native handles, or
host paths.

Each profile generation binds exact allowed origins, initial navigation targets,
network policy, and finite limits. Updating those values requires a new generation;
existing sessions do not silently inherit widened configuration.

Hosted origins require verified HTTPS. Plain HTTP is limited to explicit loopback mode.
Every resolved address must pass current browser destination policy. Mixed safe/unsafe
answer sets fail closed, redirects are finite, and every redirect destination is
re-admitted.

## Browser engine boundary

Phoenix OS v0.35.0 does not bundle a production browser engine. The reviewed
`BrowserAdapter` contract separates zero-effect preparation from protected commit. A
concrete deployment adapter must prove that preparation emits no remote request bytes
or protected browser effect before final admission.

The deterministic in-memory adapter remains suitable for tests and security validation;
it is not a network-capable browser engine.

JavaScript, autonomous background networking, automatic subresources, iframes, popups,
multiple pages, downloads, uploads, persistent browser storage, and persistent
user-data directories remain outside v0.35.0.

## Session and page migration

Browser sessions are ephemeral and bound to the exact structural authority subject that
opened them. Session, page, revision, and element identifiers are opaque Phoenix-owned
identities and are never bearer authority.

Page revisions are freshness identities. A page snapshot or element ID from an older
revision must be discarded and reacquired instead of being retargeted.

Page reads require a fresh independent `browser.page.read` authorization. Returned page
content, labels, links, forms, redirect locations, and accessibility text remain
untrusted data.

## Agent tool composition

Model-originated browser work must first pass the RFC-0027 `tool.invoke` boundary and
then the exact browser action boundary. `BrowserToolBinding` is server-owned and binds
one exact agent/tool/action/profile generation, plus a fixed navigation target when the
action is `browser.page.navigate`.

Tool arguments cannot introduce URL, selector, script, proxy, credential, cookie,
authority, executable, or host-path escape hatches.

Final tool revalidation is repeated after the last attacker-controlled preparation wait
before browser commit. A prior tool approval or ALLOW decision is not reusable browser
authority.

## Runtime ownership and shutdown

Standalone `BrowserAutomationService` instances remain available until explicitly
closed. Deployments may optionally make the Phoenix Runtime the owner.

Runtime state controls availability and shutdown only; it does not grant browser
authority. Runtime-owned services reject new work before `RUNNING` and after the Runtime
leaves `RUNNING`.

Shutdown is bounded: new operations are rejected, admitted work is drained within
server-owned limits, ephemeral sessions are closed, and owned adapter resources are
closed. Policy, identity/freshness, Event Bus, audit, observability, and resolver
dependencies are borrowed and are not closed by the browser service.

Security quarantine remains distinct from ordinary Runtime unavailability. A service
quarantined after an ambiguous or non-cooperative effect fails closed with the browser
operation-disabled semantics rather than being treated as normal lifecycle shutdown.

## Observability and administration

Routine browser telemetry is content-free. It is limited to a server-generated operation
ID, finite operation class, finite outcome, whether an effect may have started, and
bounded duration.

It does not contain page text, element labels, fill values, URLs, origins, request or
response bodies, cookies, credentials, DNS answers, literal addresses, certificate
details, native browser handles, raw adapter errors, authority intents, or policy
decisions.

Telemetry is best-effort and cannot insert an awaited observer step between final
admission and commit.

Read-only health is exposed separately through `BrowserAutomationAdministration` and
requires `browser.health.read`. The snapshot is point-in-time and content-free; it does
not enumerate profiles, sessions, pages, elements, destinations, cookies, or policy
decisions. Health authority does not imply any browser action.

## Failure and retry expectations

Before protected effect commit, callers should handle finite rejected, stale, cancelled,
timed-out, and failed outcomes.

Once a remote or external effect may have started, ambiguous failure is
`INDETERMINATE`. Phoenix does not transparently retry a potentially effectful browser
operation after that boundary.

## Release-gate adoption

Run the dedicated browser hardening gate in addition to the existing global checks:

```text
python scripts/check_browser_automation_release.py
```

The gate runs the complete browser regression suite, verifies the closed browser package
surface, validates safe wheel/sdist contents and metadata, rebuilds a wheel from the
validated sdist, and performs an isolated offline smoke test that exercises contracts
and authority-catalog shape without DNS, sockets, HTTP exchanges, or a real browser.

S7 intentionally does not change `pyproject.toml`, `CHANGELOG.md`, release notes, tags,
or publication metadata. RFC-0035 S8 performs v0.35.0 release finalization only after
the S1-S7 security and package gates are green.
