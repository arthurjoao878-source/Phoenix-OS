# Migrating from Phoenix OS v0.26.0 to v0.27.0 agent execution

Phoenix OS v0.27.0 introduces the optional RFC-0027 agent loop and tool-calling
Runtime. This guide is for deployments already using v0.26.0 inference and for
deployments that want to upgrade without enabling agent execution.

The safe default is unchanged: upgrade the package first and keep agent
configuration absent. Agent execution begins disabled and no default assistant,
tool, permission, approval, model call, worker, listener, state key, network
request, filesystem access, shell access, or operating-system action is created.

## Compatibility baseline

A v0.26.0 deployment can construct `RuntimeAssembler` without adding agent
arguments. When agent configuration is omitted:

- no `agent` service or component exists;
- no tool registry, resolver, or executable adapter is composed;
- no approval record or agent run is created;
- no agent State Store key is created;
- no agent audit fact, metric, log, or Event Bus event is emitted;
- no prompt, model response, argument, tool result, or approval evidence is
  persisted;
- independently configured RFC-0026 inference remains available;
- Control Plane, Dashboard, service accounts, webhooks, inbound events, jobs,
  workflows, audit, secrets, persistence, TLS, and network behavior remain as in
  v0.26.0.

Do not enable an agent merely because the package imports successfully. Opt-in
requires a complete reviewed closed world.

## Pre-upgrade inventory

Before installing v0.27.0, record:

1. the exact v0.26.0 package and configuration revision;
2. enabled inference providers and models;
3. exact versioned `SecretRef` dependencies used by inference or future tools;
4. current Policy Engine rules and principals;
5. current audit, Event Bus, observability, and Runtime health baselines;
6. State Store and Audit Store backups under the deployment's existing process;
7. every proposed tool, adapter, resolver, external dependency, and side effect;
8. a rollback owner and maximum acceptable canary window.

The upgrade does not migrate inference configuration into agent configuration.
Existing service accounts receive no agent or tool scopes, and no human or
machine principal receives `agent.run`, `model.infer`, or `tool.invoke`
automatically.

## Stage 1: install with agent configuration absent

Build or install the v0.27.0 package and start Phoenix exactly as before, without
passing an `AgentServiceConfiguration`.

Confirm:

- the Runtime contains no agent service names;
- no agent lifecycle event appears;
- no tool is registered;
- no approval is created;
- no agent model turn occurs;
- existing v0.26.0 health, inference, dashboard, webhook, inbound, job, workflow,
  audit, and persistence checks remain stable.

This stage is the primary compatibility proof and the fastest rollback point.

## Stage 2: validate deterministic execution without external authority

Use `DeterministicModelTurnAdapter` and deterministic fake tools first. These
adapters perform no network request and require no paid provider usage or
credential.

The deterministic validation should cover:

- one final-only run;
- one read-only tool cycle followed by a final response;
- strict rejection of an unknown tool and malformed arguments;
- one independent model authorization per turn;
- one independent tool authorization per call;
- exactly one terminal result;
- finite limits and cooperative cancellation;
- content-free observations.

A deterministic test proves Phoenix orchestration behavior. It does not prove
that a third-party model transport or tool adapter is safe.

## Stage 3: review the closed-world tool registry

The registry is the allowlisting boundary. Callers and models select only
registered identifiers.

For each tool, review and record:

- stable `ToolId`;
- bounded name and safe description;
- exact input and output schemas;
- unknown-property behavior;
- maximum encoded input and output bytes;
- finite timeout;
- effect classification;
- whether approval may be required;
- exact resolver identity and server-owned concrete resource format;
- exact adapter identity;
- secrets or external dependencies supplied by trusted composition;
- network, filesystem, database, or operating-system effects;
- idempotency and ambiguous-failure behavior;
- close and cancellation behavior.

Do not register a generic shell, unrestricted HTTP client, unrestricted
filesystem tool, arbitrary database query tool, dynamic module loader, or
operating-system control surface. Models cannot supply endpoint, credential,
module, class, callback, policy action, or raw policy resource fields.

## Stage 4: validate schemas and canonical data

Tool proposals are untrusted. Confirm that the registered schema and codec reject:

- duplicate JSON keys;
- unknown object properties;
- non-finite numbers;
- malformed Unicode;
- unsupported schema constructs;
- path or endpoint smuggling outside the reviewed schema;
- oversized strings, arrays, objects, depth, width, or encoded bytes;
- output that does not match the registered output schema.

Authorization must evaluate canonical normalized arguments. The tool resource
must be resolved by trusted server-side code only after validation. A
model-provided string must never be copied directly into the policy resource.

## Stage 5: configure independent policy decisions

Create separate deny-by-default policy rules for:

- `agent.run` on the configured agent resource;
- RFC-0026 `model.infer` on the exact provider and model resource for every turn;
- `tool.invoke` on the exact server-resolved tool resource for every call.

Authorizing `agent.run` does not authorize nested model or tool work. Authorizing
`model.infer` does not authorize a tool. Administrative access does not grant
execution access.

Test denial at each layer and confirm that the model is not asked to bypass or
reinterpret the decision.

## Stage 6: configure exact approvals for sensitive effects

Read-only classification is not a substitute for policy, but tools with
reversible write, irreversible write, or external communication effects should
be reviewed for mandatory human approval.

Approval evidence must be bound to:

- exact tool;
- exact resolved resource;
- canonical argument digest;
- run, step, and call identifiers;
- approving actor;
- finite expiry;
- one consumption.

Verify that changing any tool, argument, resource, actor, run, step, or call
identifier invalidates the approval. Verify denial, expiration, replay,
cancellation, and shutdown behavior. Do not display or log approval tokens.

## Stage 7: configure conservative limits

Begin below global ceilings. Set finite values for:

- agent steps and model turns;
- total tool calls and one tool call per turn;
- prompt, model-output, argument, result, and accumulated tool-result bytes;
- input and output tokens;
- structured-data depth and item count;
- queue depth and concurrent runs;
- concurrent model and tool calls;
- model-turn, tool-call, approval-wait, and total-run timeouts;
- cancellation and shutdown grace.

The most restrictive applicable limit wins. Validate global and configured-agent
saturation before canary traffic. Admission must occur before model execution,
credential leasing, approval creation, or tool execution.

## Stage 8: inspect content-free operations

Enable only the observation sinks required by the deployment. Safe audit,
metrics, logs, health, administration, and Event Bus observations may contain
stable identifiers, operation and outcome categories, tool identifier, effect,
argument digest, resolved-resource category, counts, duration, queue state, and
safe failure category.

They must exclude prompts, model responses, raw arguments, tool results,
credentials, secret references, approval tokens, endpoint details, external
response bodies, and raw exceptions. Event Bus observations use fixed
Phoenix-owned event types and empty payloads.

Review sink retention and access separately. Do not add temporary content logging
to diagnose canary failures.

## Stage 9: run a conservative canary

Enable one configured agent for one trusted principal and the smallest reviewed
tool set. Prefer a deterministic or read-only tool before any external side
effect.

During the canary, verify:

- exact run, model, and tool authorization counts;
- no unregistered tool exposure;
- schema failures occur before authorization and execution;
- approval challenges bind the exact invocation;
- serial tool execution within one run;
- global, agent, model, and tool saturation behavior;
- finite timeout and cancellation cleanup;
- no transparent retry of model or tool execution;
- ambiguous tool failure returns an indeterminate safe category;
- reverse adapter close order and bounded shutdown;
- inference shutdown ordering remains intact;
- observations remain content-free.

Any caller retry must be explicit and domain-aware. Never automatically repeat a
side-effecting call based only on a timeout or transport failure.

## Rollback procedure

Rollback should first remove agent authority, not delete shared state or secrets.

1. Reject new agent runs at the service boundary.
2. Disable every active tool through maintainer administration when the Runtime
   is still healthy.
3. Remove or deny `agent.run` and `tool.invoke` policy grants.
4. Allow active runs to drain or cancel within the configured finite grace.
5. Stop the Runtime so unused approvals are invalidated and adapters close in
   reverse composition order.
6. Remove agent configuration and restart Phoenix.
7. Confirm there is no agent service, tool registry, event, approval, or active
   run.
8. Keep RFC-0026 inference configured when it is independently required.
9. Reinstall the previously recorded v0.26.0 artifact only when package rollback
   is necessary.

Preserve exact `SecretRef` versions, inference configuration, unrelated State
Store records, audit records, service accounts, webhook state, inbound state,
jobs, workflows, sessions, and Control Plane configuration. RFC-0027 creates no
persistent agent run records, so unrelated Phoenix state survives enablement and
rollback.

After an ambiguous external tool failure, reconcile with the external system
before another invocation. Disabling the agent prevents new work but cannot undo
a side effect already committed by an external adapter.

## Release and package validation

Run the full quality gate from a clean checkout:

```text
python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pytest -q
python scripts/check_webhook_release.py
python scripts/check_inbound_release.py
python scripts/check_inference_release.py
python scripts/check_agent_release.py
```

The agent release gate must validate the threat review, migration guide, ADRs,
RFC status, release metadata, and selected security suites. It must build wheel
and sdist artifacts, reject unsafe archive paths and sensitive file types,
rebuild a wheel from the validated sdist, and install both wheels with
`--no-deps --no-index` in isolated offline environments.

The isolated smoke execution must import from the installed environment rather than the source tree and without source-tree imports and exercise a deterministic final run, one strict tool
cycle, exact actions and resources, immutable configuration, content-free
observation, and package version 0.27.0.

## Final rollout checklist

- [ ] v0.26.0 baseline captured
- [ ] v0.27.0 starts with agent configuration absent
- [ ] deterministic final-only run passes
- [ ] deterministic strict tool cycle passes
- [ ] registry and adapter review complete
- [ ] schemas reject ambiguous and unknown input
- [ ] independent run/model/tool policy rules tested
- [ ] sensitive effects require exact single-use approval
- [ ] finite budgets and admission tested
- [ ] cancellation and shutdown remain bounded
- [ ] no transparent retry is configured
- [ ] content-free audit and observability verified
- [ ] rollback owner and procedure tested
- [ ] full quality and isolated package gates pass
