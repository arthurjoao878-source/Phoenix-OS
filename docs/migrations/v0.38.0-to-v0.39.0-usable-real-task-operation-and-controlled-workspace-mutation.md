# Migration: Phoenix OS v0.38.0 to v0.39.0 usable real-task operation and controlled workspace mutation

RFC-0039 adds the official operator task path plus bounded controlled development-checkout
workspace mutation. It reuses existing Phoenix configuration, inference, agent, integrated,
durable, workspace, authority, approval, and recovery boundaries rather than creating a
parallel authority model.

This document describes release-candidate migration and rollback guidance. RFC-0039 remains
Proposed until the final release gate and separately invoked real-provider dogfood are green.

## Compatibility default

No migration action is required when RFC-0039 configuration is omitted. Existing v0.38
provider-neutral execution remains valid. Package installation alone contacts no provider,
registers no development checkout, grants no workspace patch authority, and performs no
workspace mutation.

## Official operator path

Reviewed deployments use the official package entrypoints:

- `phoenix config validate`
- `phoenix doctor`
- `phoenix task run`
- `phoenix task status`
- `phoenix task resume` when applicable

The normal path must not depend on a task-specific or custom Python composition helper.

## Development checkout registration

Development checkouts require explicit trusted roots. Dynamic discovery is non-authoritative.
`read_prefixes` constrain bounded list/read discovery, and `patch_prefixes` must remain a
reviewed subset appropriate for mutation.

`workspace.list` is bounded one-level discovery. `workspace.read` creates an exact current-run
snapshot and consumes finite read budget. Neither surface grants ambient filesystem access.

## Controlled workspace patch

A patch may target only an admitted observed file beneath configured patch prefixes. Preparation
fails closed for traversal/alias escapes, VCS metadata, active configuration/policy/state,
active runtime/venv targets, binary or invalid UTF-8 content, special/reparse files, unsafe
metadata, excessive links, stale or unobserved bases, resource rebirth, malformed edits, and
size/budget violations.

Trusted review presents the bounded exact diff. Approval binds to that exact prepared patch.
Immediately before physical effect, Phoenix revalidates authority, approval, identity,
freshness, cancellation, deadline, bounds, and protected-target state. Indeterminate effects
are not blindly replayed.

## Operator result and evidence

Normal result/status evidence remains content-free. Operators receive bounded metadata such as
changed-file count, review status, digests, budgets, and terminal reason rather than raw
workspace content in routine logs/audit/metrics.

## Real-provider dogfood

Real-provider dogfood is a separate explicit procedure. It uses an official candidate wheel in a
clean virtual environment, explicit reviewed local provider/model/profile configuration, and the
official product path.

The normative checklist is
`docs/rfcs/RFC-0039-real-provider-dogfood-checklist.md`. At minimum it covers provider
unavailability, manual provider start, doctor readiness, a real-model task, bounded list/read,
observed-file patch proposal, trusted diff, exact approval, physical patch result, stale and
unsafe-target rejection, provider interruption, durable resume/revalidation, finite task status,
no shell/Git authority, and content-free evidence.

## Rollback guidance

Rollback means removing or disabling the new trusted configuration and returning to the prior
v0.38 operational mode. Do not reinterpret existing durable state as patch authority. Do not
rewrite evidence, approval, digests, or durable history to simulate an older state.

Repository release-candidate metadata rollback must restore exact preimages and remove only
new candidate files created by the failed mutation gate. No Git lifecycle recovery command is
required for that controlled rollback.

## Release gate

Before RFC-0039 can move from Proposed to Accepted, the final v0.39 release gate and separately
invoked real-provider dogfood must satisfy the RFC. Ordinary CI stays deterministic and
network-free. Acceptance, commit, push, tag, and publication remain separate reviewed actions.
